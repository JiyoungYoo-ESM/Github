# 신규 EU 발주 로직 개선을 위한 데이터 기반 검토 보고서

**부제:** CMS API 데이터 기반 월별 예측 · 주차 재고전망 PoC 결과
**기준일:** 2026-07-06 ｜ **데이터 범위:** 2024-07-01 ~ 2026-07-06 (CMS 읽기 전용 조회)
**작성 목적:** 운영 반영 전 데이터 적합성 검토 (공유용 · 운영 문서 아님)
**대상 독자:** 영업 · SCM · 운영 · 기획 (비개발자 포함)

> 결론 요약: **월별 판매 예측 · 주차 재고전망 = 가능 / 완성형 자동 산식 = 부분 가능 / 완전한 백테스트 = 불가**

---

## 1. 한눈에 보는 결론 (Executive Summary)

- **판매 데이터는 새 발주 로직을 시험하기에 충분히 의미가 있습니다.** CMS에서 25개월치 판매 이력(28만 건)이 실제로 조회되어, **월별 판매 예측**과 **주차 단위 재고전망** PoC가 지금 데이터로 가능합니다.
- 다만 **완전 자동 발주 로직으로 가려면 재고·입고 이력 데이터 보강이 먼저**입니다. “품절이라 못 판 건지, 원래 안 팔린 건지”를 구분할 **일별 재고 기록**과 프로모션·상품코드·실제 입고일 정보가 현재 시스템에 없습니다.
- 따라서 **다음 단계는 화면 개발이 아니라, 이력 데이터를 쌓는 기반(저장소)을 만드는 것**입니다. 과거는 되돌릴 수 없으므로 축적을 빨리 시작할수록 유리합니다.

---

## 2. 현재 데이터로 가능한 것

| 항목 | 가능 여부 | 근거 데이터 |
|---|---|---|
| 월별 판매 추세 분석 | 가능 | 25개월 판매 이력, 월별 집계 가능 SKU 2,182개 |
| SKU별 주별 판매 집계 | 가능 | 총 48,987 판매주, 8주 이상 집계 가능 1,391 SKU |
| 기존 3개월 평균 vs 월별 예측(추세 반영) 비교 | 가능 | 200개 SKU 시연 완료 |
| 현재 재고 + 운송중 ETA 기반 8주 재고전망 | 가능 | SKO 재고 + 운송중 ETA 주차 전개 |
| 진짜 주차별 수요 예측 | 부분 가능 | 주 평균은 가능하나 품절 보정은 일별 재고 로그 필요 |

### 확보된 데이터 규모

| 데이터 | CMS 엔드포인트 | 행/SKU 수 |
|---|---|---:|
| SKO 현지재고 | /eu/stock/local | 2,365 SKU |
| 본사 EU창고 재고 | /eu/stock/hq | 2,959 SKU |
| EU 현지판매 | /eu/sales/local | 282,683 행 |
| 본사→EU 출고 | /eu/sales/hq-to-eu | 12,415 행 |
| 운송중(컨테이너) | /eu/shipping/containers | 1,977 행 |
| 미입고 PO | /eu/open-po | 1,689 행 |

### 판매 이력 “품질” 분포 — 첫 번째 주의점

추세 예측이 신뢰성 있게 되려면 이력이 12개월 이상이어야 하는데, 그런 SKU는 전체의 약 1/4뿐입니다.

| 판매 이력 길이 | SKU 수 | 의미 |
|---|---:|---|
| 12개월 이상 | 542 | 추세(Holt) 예측 신뢰도 높음 — 우선 적용 대상 |
| 6~11개월 | 613 | 제한적 예측 — 단순평균 + 버퍼 |
| 6개월 미만 | 1,027 | 이력 부족 — 신상/차용 통계, 사람 검토 필요 |
| (참고) 월별 판매 급변 SKU | 1,254 | 프로모션·벌크딜 분리 전엔 예외 검토 필요 |

### 기존 방식 vs 새 방식 — 발주량 비교 (200개 SKU 시연)

| 방식 | 추천 발주량 합계 | 특징 |
|---|---:|---|
| 기존 (3개월 평균) | 44,487 | 모든 상품 동일 규칙 |
| 월별 예측 (추세 반영) | 29,660 | 최근 흐름·추세 반영 |
| 주차 재고전망 | 21,617 | “언제 비나”를 날짜로 계산 |

> ⚠ **이 숫자를 “절감액”으로 읽으면 안 됩니다.** 비교 대상 200개는 SKU 코드 앞부분(알파벳순) 표본이라 신상·저이력 상품이 많이 섞여 있습니다. 방식 간 차이가 크게 벌어진 것은 **“방식이 다르게 계산된다”는 방법론 시연이지, 검증된 재고 절감 효과가 아닙니다.** 실제 효과는 병행 운영으로 확인해야 합니다. (8주 내 소진 위험 50개 SKU 식별, 방식 간 발주량 차이 큰 SKU 약 20여 개)

## 3. 현재 데이터의 한계

아래 항목은 CMS API에 **아예 없다고 확인된** 데이터입니다.

| 없는 데이터 | 왜 중요한가 · 없으면 생기는 문제 |
|---|---|
| 품절일수 (sellable_days) | 판매가 적은 이유를 구분 못 함. 품절이라 못 판 건데 “수요 없음”으로 학습 → 발주 과소 → 만성 품절 |
| 프로모션·벌크딜 표시 | 일회성 대량 주문이 일반 수요로 섞여 예측이 부풀려짐 (통계 오염 1순위) |
| 상품코드 통합 (SKU alias) | 코드가 바뀐 상품은 이력이 끊겨 “신상”으로 오인, 추세를 못 살림 |
| 실제 도착일 (arrival_date) | 실제 리드타임을 못 배워 운송 지연 위험을 정확히 못 봄 |
| ETA(도착 예정) | 운송 API에 없음 → 출고일 + 예상 소요일로 계산(추정치) |
| PO 등록일 · 납품 예정일 · 실제 입고일 | 브랜드 주문의 “언제 들어오나”를 계산 못 함 → 브랜드 주문(Q2)은 “대략 수량”까지만 |
| MOQ · 유통기한 | MOQ 없으면 주문량 반올림 불가, 유통기한 없으면 과잉 발주 시 폐기 위험 못 거름 |

> **가장 근본적인 한계 — 과거 재고 스냅샷 없음.** CMS는 “오늘 현재 재고”만 줍니다. 지난달 어느 날 재고가 있었는지(품절이었는지)는 알 수 없어, **완전한 백테스트는 불가**합니다. 단, 예측 정확도 검증은 판매 이력만으로 부분적으로 가능합니다.

## 4. 비개발자용 쉬운 설명

> **지금 시스템은 “오늘 사진 한 장”은 잘 찍습니다.** 현재 재고·최근 판매·운송중·미입고를 알려주니, 지금 발주가 필요한지 판단하는 데는 충분합니다.
>
> **그런데 새 발주 로직에는 “일자별 기록 영상”이 필요합니다.** 지난 몇 달 어떻게 팔렸고, 언제 품절이었고, 언제 입고됐는지를 봐야 하니까요. 사진 한 장으로는 “지난달 15일에 재고가 있었는지”를 알 수 없습니다.
>
> 부족한 건 **화면 문제가 아니라, 이 과거 기록이 쌓이지 않는 구조**입니다.

### 예를 들면 — 지난달에 10개만 팔린 상품

| 겉보기 | 실제 이유 | 올바른 발주 |
|---|---|---|
| 10개 판매 | 진짜 수요가 10개뿐 | 적게 발주 (정상) |
| 10개 판매 | 25일 품절이라 10개밖에 못 팖 | 넉넉히 발주 (실제 수요는 훨씬 큼) |

현재 데이터로는 이 둘을 구분하기 어렵습니다. **일별 재고 기록**이 있어야 “품절 때문이었다”를 알고 판매량을 보정할 수 있습니다.

## 5. 개선 방향 (우선순위)

| 순위 | 할 일 | 기대 효과 |
|---:|---|---|
| 1 | 일별 재고 스냅샷 저장 시작 (또는 CMS/ERP 과거 일별 재고 로그 API 확보) | 품절 보정의 핵심 재료 확보 |
| 2 | 프로모션·벌크딜·FOC·반품 식별 강화 | 예측 오염 제거 |
| 3 | 상품코드 통합(SKU alias) 마스터 구축 | 끊긴 판매 이력 연결 |
| 4 | ETA + 실제 도착일 확보 | 정확한 리드타임 · 지연 감지 |
| 5 | PO 생애주기(등록일·예정일·입고일) 데이터 확보 | 브랜드 주문(Q2) 시점 계산 완성 |
| 6 | MOQ · 유통기한 · 상품마스터 연결 | 주문량 반올림 · 폐기 위험 방지 |

## 6. 추천 저장 구조 (기억 창고)

“현재 재고”가 아니라 **“시간에 따른 재고 상태”**를 저장하기 위한 최소 구조입니다. 처음엔 실험용 SQLite로 시작하고, 검증 후 IT팀 정식 DB로 옮깁니다.

| 테이블 | 무엇을 저장 | 주요 컬럼 | 채우는 방법 |
|---|---|---|---|
| daily_stock_snapshot | 매일의 SKU별 재고 상태 | date, prod_cd, 창고, 재고/Hold/가용, 품절여부 | 매일 재고 API 저장 (또는 ERP 일별로그) |
| sales_fact | 판매 원장(집계 재료) | ship_dt, prod_cd, qty, amount, biz_type, site | 판매 API 누적 적재 |
| shipping_lifecycle | 운송 건 상태 이력 | pckg_no, prod_cd, mode, 출고일, ETA추정, **도착일** | 운송 API + 도착 확인 |
| po_lifecycle | PO 건 상태 이력 | po_no, prod_cd, **발주일·예정일·입고일**, 수량 | 미입고 API + 발주/입고 이벤트 |
| sku_alias | 코드 통합 매핑 | old_cd, canonical_cd, 전환일 | 운영자 관리 |
| promo_event | 프로모션·벌크딜 기간 | prod_cd, 시작·종료, 유형, 예상물량 | 영업·MD 입력 |
| product_master_ext | MOQ·유통기한 | prod_cd, moq, 아웃박스, 유통기한 | 운영자·브랜드사 |

> **왜 DB가 필요한가:** 매번 CMS에서 24개월치를 다시 받으면 느리고, “과거 어느 날의 재고”는 애초에 CMS가 주지 않습니다. 매일 조금씩 저장해 시간축 기록을 만드는 것이 목적입니다. 저장은 **회사 서버 안에서, 고객정보 없이 요약 숫자 위주**로 하면 보안 부담을 최소화할 수 있습니다.

## 7. 단계별 로드맵

| 시점 | 작업 |
|---|---|
| 즉시 | 실험용 SQLite(또는 별도 실험 DB) 생성 — 판매·재고 이력 적재 시작, 정합성 검증 |
| +1개월 | 일별 재고 스냅샷으로 품절일수 계산 시작 |
| +3개월 | 품절 보정(sellable_days) 초안 테스트, 프로모션 분리 절차 적용 |
| +6개월 | 월별 예측 산식 후보 비교(기존 vs 추세), 병행 검증 |
| +12개월 | 백테스트 체계화, 계절 패턴 학습 검토 |

> **단축 가능:** CMS/ERP에 이미 과거 일별 재고 로그가 있고 API로 받을 수 있다면, 새로 쌓을 필요 없이 위 일정을 크게 앞당길 수 있습니다. — 이 확인이 이번 검토의 가장 중요한 후속 질문입니다.

## 8. 의사결정이 필요한 사항

- **CMS/ERP에 과거 SKU별 일별 재고 로그가 있는가?** (있으면 축적 없이 바로 확보 가능)
- 있다면 **API로 제공 가능한가?** 없다면 **오늘부터 매일 스냅샷 저장을 시작할지** 결정
- **프로모션·벌크딜 / SKU alias / 실제 도착일**을 어느 시스템(운영자 표, CMS, ERP)에서 관리할지 결정
- 실험용 저장소를 **회사 서버 안 SQLite**로 시작하는 것에 대한 **보안 검토·승인**

---

## 9. 결론

- **현재 데이터는 PoC(개념 검증)에는 충분히 의미가 있습니다.** 월별 예측·주차 재고전망은 지금 됩니다.
- **운영 자동화 수준으로 가려면 데이터 기반 보강이 먼저입니다.** 품절·입고·프로모션·코드 변경 이력이 핵심입니다.
- **화면 개발보다 데이터 저장·정합성 확보가 우선입니다.** 과거는 되돌릴 수 없으니 축적을 빨리 시작할수록 유리합니다.
