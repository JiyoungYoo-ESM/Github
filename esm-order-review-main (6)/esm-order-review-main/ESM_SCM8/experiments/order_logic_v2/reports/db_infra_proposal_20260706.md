# CMS 데이터 기반 발주 분석 DB 도입 근거 · 요청서 — 인프라/DB팀 협의용

**기준일:** 2026-07-06 ｜ **요청 부서:** EU SCM (발주 로직 고도화 과제) ｜ **대상:** 인프라 / DB팀
---

## 1. Executive Summary

신규 EU 발주 로직은 단순히 현재 재고와 최근 3개월 판매량만 보는 방식이 아니라, **SKU별 판매 이력, 일별 재고 변화, 품절일수, 운송 ETA, 미입고 PO, 계산 결과 이력**을 함께 봐야 합니다.

현재 CMS API는 발주 분석에 필요한 원천 데이터를 가져오는 통로로 활용되고 있습니다. 다만 신규 로직을 검증·운영하려면 “오늘 조회한 값”뿐 아니라 **기준일별 데이터와 계산 결과를 재현할 수 있는 이력 저장 구조**가 필요합니다.

따라서 이번 협의의 핵심은 CMS 데이터를 발주 분석 관점에서 **기준일별로 저장·검증할 수 있는 공식 데이터 경로를 함께 정하는 것**입니다.

---

## 2. 한 줄 요청

> **SKU별 일별 재고 이력·기준일별 계산 결과를 재현할 데이터 조회 또는 저장 구조가 필요합니다** — CMS에 이력이 이미 있으면 그 **조회 방법**을, 없으면 **분석용 저장 구조**를 함께 확인·검토하고자 합니다.

우선순위:

```text
1순위: CMS 또는 CMS DB에 이미 있는 일별 재고 이력 조회
2순위: 인프라팀 표준 DB/스키마에 분석용 스냅샷 저장
3순위: 검증 단계 한정 임시 저장소로 PoC 수행
```

---

## 3. 현재 구조와 한계

현재 ESM 발주 분석 웹은 CMS API를 호출해 데이터를 가져오고, 그 데이터로 계산한 뒤 화면·엑셀 결과를 제공합니다.

```text
CMS API 호출
→ 재고 / 판매 / 운송중 / 미입고 PO 데이터 수집
→ 발주 분석 계산
→ 화면 / 엑셀 출력
→ 종료
```

문제는 이 구조가 기본적으로 **무상태(stateless)** 라는 점입니다. 계산이 끝난 뒤 “그 기준일에 어떤 데이터로 어떤 결과가 나왔는지”가 체계적으로 누적되지 않습니다. 기존 단순 발주 검토에는 어느 정도 가능했지만, 신규 발주 로직에서는 한계가 있습니다.

---

## 4. 왜 CMS API 실시간 조회만으로 부족한가

**① 과거 기준일 재현이 어렵다.** 신규 로직은 이런 질문에 답해야 합니다:

```text
지난달 15일에 이 SKU는 품절 상태였는가?
그 달 판매량이 낮은 이유가 수요 감소였는가, 재고 부족이었는가?
운송중 물량은 그 기준일에 실제로 언제 도착 예정이었는가?
그때 계산한 발주 추천량은 이후 실제 결과와 비교했을 때 맞았는가?
```

CMS API가 오늘 기준 스냅샷만 제공한다면 과거 특정일의 재고 상태를 재현할 수 없고, 특히 `sellable_days`(판매 가능일수) 계산이 어렵습니다.

**② 성능 문제.** 최근 24개월 판매 이력을 매번 실시간 API로 가져오면 응답 시간이 길어집니다(인보이스 라인 단위라 데이터량이 큼). 반복 조회되는 데이터는 **기준일별·집계 단위로 저장**하고, 발주 분석은 저장된 이력을 조회하는 방식이 더 안정적입니다.

**③ 계산 결과 설명과 감사 추적.** 신규 로직은 월별 수요예측, 예측오차 σ_E, ABC/XYZ 등급, 안전재고, 목표재고, 운송수단 추천, 품절 예상일, 브릿지 운송량, 브랜드 PO 필요량, 예외 플래그를 계산합니다. 이 결과를 나중에 설명하려면 **당시 입력 데이터·파라미터·산식 버전·계산 결과**가 함께 남아야 합니다.

## 5. 필요한 데이터 범위

**SKU 마스터** — 상품코드 · 상품명 · 브랜드 · 카테고리 · SKU alias/통합코드 · MOQ · 아웃박스 수량 · FR Date/유통기한 · 판매 가능 여부 · 단종 여부

**판매 이력** — SKU · 판매일(또는 월) · 판매수량 · 판매금액 · Biz Type · Site · 창고 · 거래처 · 반품 여부 · FOC 여부

**재고 이력** — 기준일 · SKU · 창고 · 총재고 · Hold 수량 · 가용재고 · 재고>0 여부

**운송 이력** — Packing No · Invoice No · SKU · 수량 · 운송수단 · 출고일 · ETA · 실제 도착일 · 도착 창고

**미입고 PO** — PO No · SKU · PO 수량 · 미입고 수량 · PO 등록일 · 브랜드 납품 예정일 · 실제 EU창고 입고일

**보정 데이터** — 프로모션 기간 · 벌크딜 여부 · 특판 여부 · 예상 물량 · 담당자 메모

## 6. DB / 이력 저장이 필요한 이유

DB는 CMS를 대체하기 위한 것이 아닙니다. 역할이 다릅니다.

- **CMS:** 원천 데이터를 관리하고 API로 제공하는 시스템
- **발주 분석 DB:** CMS에서 조회한 데이터를 기준일별로 저장하고, 발주 로직 계산 결과를 재현·검증하기 위한 분석용 저장소

분석 DB가 필요한 이유:

1. 과거 기준일별 재고 상태 보존
2. sellable_days 계산
3. 월별/주별 수요예측 검증
4. 예측오차 σ_E 계산
5. 기존 로직 vs 신규 로직 병행 비교
6. 품절일수 / 과재고 / 항공 추천 결과 검증
7. 계산 결과 재현
8. 파라미터 변경 이력 관리
9. 산식 버전별 결과 비교
10. 운영 전환 전 백테스트

---

## 7. 저장 대상과 민감도

- **저장 대상:** SKU별 판매수량 · 재고수량 · 운송중 수량 · PO 수량 · 창고/운송/입고 일정 · 계산 결과
- **저장하지 않는 대상:** 소비자 이름 · 연락처 · 주소 · 결제 개인정보

거래처명·금액·재고수량은 내부 운영/재무 데이터로 접근 권한·보관 정책은 필요하지만, 소비자 개인정보와는 성격이 다릅니다.

---

## 8. 용량과 운영 영향

| 테이블 | 예상 규모 | 비고 |
|---|---:|---|
| daily_stock_snapshot | 연 ~180만 행 | SKU 약 5,000 × 365일 |
| sales_fact | 연 ~10~20만 행 | 인보이스 라인 기준 |
| sales_monthly | 연 수만 행 이하 | SKU × 월 집계 |
| shipping / po_lifecycle | 연 수천~수만 행 | 운송·PO 상태 이력 |
| 마스터 데이터 | 수천 행 | 거의 정적 |

인덱스·백업을 포함하더라도 **원천 CMS DB 대비 작은 규모**이며, 검증 단계에서는 **수백 MB 수준**, 운영 보관 기간에 따라 **수 GB 이내**로 관리 가능한 규모로 예상됩니다.

## 9. 대안 비교

| 대안 | 장점 | 한계 · 조건 | 판정 |
|---|---|---|---|
| 1. CMS API 실시간 조회만 | 별도 저장소 불필요 | 과거 재고 재현 어려움, 24개월 조회 성능 부담, 백테스트 어려움 | 신규 로직 검증에는 **부족** |
| 2. 현재 파일 캐시 | API 호출 부하 일부 완화 | 임시 캐시라 감사·재현·이력 관리에 부적합 | 검증용 DB **대체 불가** |
| 3. CMS/CMS DB 기존 이력 조회 | 중복 저장 최소화, 가장 이상적 | 일별 재고·입고·운송 이력이 이미 존재해야 함 | **1순위 확인** |
| 4. 별도 분석용 스냅샷 저장소 | 기준일별 재현·백테스트·계산 결과 저장 | 인프라팀 표준 DB/권한/백업 정책 필요 | 이력 없을 경우 **필요** |

## 10. 인프라팀 핵심 질문

1. **(최우선)** CMS 또는 CMS DB에 SKU별 일별 재고 이력이 이미 저장되어 있나요? *(CMS API로는 현재 재고만 나오지만, 백엔드 DB에는 과거가 남아 있을 수 있음)*
2. 있다면 발주 분석 시스템에서 조회할 수 있는 API · View · 읽기 계정을 제공받을 수 있나요?
3. 없다면 오늘부터 SKU별 일별 재고 스냅샷을 분석용으로 저장해도 될까요?
4. CMS API 응답 데이터를 내부 분석 검증 목적으로 저장해도 될까요?
5. 저장 위치는 어디가 적절한가요?
6. 운영 전환 시 표준 DB·백업·권한 정책을 어떻게 적용하면 될까요?
7. 보관 기간은 어느 정도가 적절한가요?
8. 프로모션·SKU alias·실제 도착일 같은 보정 데이터는 어느 시스템에서 관리하는 것이 적절한가요?

| Phase | 내용 |
|---|---|
| 0. 데이터 존재 확인 | CMS/CMS DB에 일별 재고 이력이 있는지 + 판매/운송/PO 과거 이력 조회 가능 여부 확인 |
| 1. 검증용 진단 | CMS API 읽기 전용 호출, 월별/주별 판매 집계 가능성 확인, 부족 필드 목록화 |

## 14. DB / 이력 저장이 없을 경우 리스크

1. 과거 기준일 재고 재현 불가
2. 품절일수 계산 불가
3. 판매 0이 “수요 없음”인지 “품절 때문”인지 구분 불가
4. 월별/주별 예측 정확도 검증 불가
5. 예측오차 σ_E 계산 신뢰도 저하
6. ETA 지연률 보정 불가
7. 기존 로직과 신규 로직 병행 검증 어려움
8. 계산 결과 설명 / 감사 추적 어려움
9. 파라미터 변경 전후 비교 불가
10. 운영 전환 전 백테스트 불가

---

## 15. 최종 요청 문장

> 신규 발주 로직 검증을 위해서는 SKU별 일별 재고 이력과 기준일별 계산 결과를 재현할 수 있는 **데이터 조회 또는 저장 구조**가 필요합니다.
>
> 먼저 **CMS 또는 CMS DB에 일별 재고 이력이 이미 저장되어 있는지 함께 확인**하고자 합니다. 이력이 있다면 별도 저장소를 만들기보다, 해당 데이터를 발주 분석 시스템에서 조회할 수 있는 방식(API · View · 읽기 계정 등)을 **우선 검토하고 싶습니다.**
>
> 만약 현재 CMS가 **오늘 기준 스냅샷만 제공**한다면, 검증 기간 동안 일별 재고 스냅샷과 계산 결과를 내부 분석용 저장소에 적재하는 방식이 가능한지 **인프라 관점에서 의견 부탁드립니다.**
