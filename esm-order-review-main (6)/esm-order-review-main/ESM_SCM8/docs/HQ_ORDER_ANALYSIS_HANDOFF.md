# 본사 오포 발주분석 도입 인수인계

마지막 갱신: 2026-08-24
현재 상태: HQ/OPO V2 연동 완료 — 91일 수요 관측기간 반영

## 0. 이 문서의 사용법

본사(`HQ`) 선택 시 오포 창고 국내 B2B 발주분석을 제공하는 작업을 수정하거나
검토하기 전에 이 문서를 끝까지 읽는다. 표준편차 기반 신규 발주 로직 V2를
사용하거나 변경하는 작업이면
[`ORDER_LOGIC_V2_HANDOFF.md`](ORDER_LOGIC_V2_HANDOFF.md)도 함께 읽는다.

이 문서에서 사용하는 상태는 다음과 같다.

- **확정**: 회의에서 명시적으로 합의된 내용
- **잠정**: 인터뷰 방향은 확인했지만 최종 승인 표현은 아직 받지 않은 내용
- **미결**: 구현 전에 사용자의 답변 또는 업무 책임자의 승인이 필요한 내용
- **제안**: 안전한 구현을 위한 설계안이며 확정값이 아님

회의 요약보다 사용자의 이후 명시적 결정이 우선한다. 결정되지 않은 산식,
기본값, 필터, fallback을 코드에 추정해 넣지 않는다. 회의 원문이나 실제 CMS
원천 데이터는 저장소에 복사하지 않는다.

## 1. 지금 단계의 결론

### 1.1 업무 프레이밍

| 항목 | 현재 정의 |
| --- | --- |
| 의사결정자 | **미결** — 본사 구매/SCM 파일럿 책임자와 제품 책임자 중 누가 산식·출시를 최종 승인하는지 지정 필요 |
| 비즈니스 목표 | 사용자가 본사를 선택했을 때 OPO 국내 B2B의 재현 가능한 발주 제안을 조회하고, 파일럿 결과로 확대 여부를 판단한다. |
| 문제 상황 | HQ는 판매이력만 부분 연결돼 있고 발주에 필요한 재고·PO·입고 계약이 없으며, 현 V2는 PL/EU 정책에 결합돼 있다. |
| 범위와 시계 | 2026년 8월 파일럿 계획을 재확인하고, 후보 브랜드·최근 91일 수요·최근 12개월 리드타임·0/2/4주 평가를 다룬다. |
| 제약 | 미결 산식·필터·fallback을 추정하지 않고, PL과 레거시 결과를 바꾸지 않으며, 실제 구매 전송 전 shadow 검증을 거친다. |
| 지원할 결정 | HQ에 어느 발주분석 화면과 산식을 열지, 파일럿이 안전한지, 이후 대상 브랜드를 확대할지를 결정한다. |
| 성공/가드레일 | 평가지표는 최대 3개와 G/Y/R로 제한하되 수치 경계는 미결이다. 법인 혼입 0건, 원천 대사 통과, PL 회귀 불변은 필수 가드레일이다. |

**사실**은 회의 합의와 현재 코드로 확인한 내용이다. **잠정 방향**은 사용자
인터뷰에 따라 HQ에서는 V2만 진행하고 기존 발주분석은 열지 않는 것이다.
표현이 잠정적이므로 최종 승인으로 간주하지 않는다. **열린 질문**은 2.2절과
5절에 모아 두고 답을 받기 전 구현값으로 사용하지 않는다.

본사 발주분석은 화면 차단을 해제하거나 기존 PL API를 한 번 더 연결하는 정도의
작업이 아니다. V2의 원천 매핑, 정책값, 시간대, 통화, 화면 문구와 Excel이
PL/EU 의미에 강하게 결합되어 있기 때문이다.

> **2026-08-14 갱신**: 이 문서가 처음 작성된 시점에는 본사 재고·미입고·
> 구매오더·실입고 API 계약이 없었다. 현재는 운영 CMS에 `/opo/inventory`,
> `/opo/po/open`, `/opo/inbound/confirmed`, `/opo/inbound/history`,
> `/opo/leadtime/stats`가 존재하며 결정 로그 `HQ-011`~`HQ-015`로 매핑을
> 확정했다. 아래 6절 체크리스트는 확정된 계약과 대조하는 용도로 유지한다.

특히 **프런트와 라우터의 HQ 차단만 제거해서는 안 된다.** 현재 V2 서비스는
법인 코드를 원천 조회 함수에 전달하지 않고 기본값 `PL`을 사용한다. 차단만
제거하면 사용자가 본사를 선택했는데 PL 원천으로 계산된 결과가 나올 수 있다.
이는 이 기능에서 가장 먼저 막아야 하는 중대 오류다.

권장 진행 순서는 다음과 같다.

```text
업무 범위·산식 결정
  -> HQ/OPO API 계약 작성 및 원천 대조
  -> HQ 전용 source adapter와 정책 snapshot
  -> shadow 계산(구매 실행 금지)
  -> 화면·Excel·권한 검증
  -> 파일럿 브랜드 한정 운영
  -> 0주/2주/4주 평가와 확대 여부 결정
```

## 2. 회의에서 확인된 범위

### 2.1 확정된 업무 방향

- 파일럿 대상은 본사 CMS의 오포 창고 코드 `OPO`다.
- 대상 사업은 본사 국내 B2B다.
- 2026-08-24 사용자 결정에 따라 수요 표본은 현재일을 제외한 최근 완료 91일을
  사용한다. 2026-08-15의 84일 결정은 이 결정이 대체한다(HQ-023, RS-024).
- 본사 운영 리드타임의 기본 개념은
  `구매오더 생성일 -> 실제 입고일`이다.
- 리드타임 변동성 관측기간은 최근 12개월을 목표로 한다.
- 12개월 원천 확보 전까지 6개월 사용 가능성이 논의됐지만, 자동 fallback
  조건은 아직 확정되지 않았다.
- 파일럿 후보 브랜드는 라운드랩, 센텔리안24, 성분에디터다.
- 실제 파일럿 브랜드는 공급 히팅률을 확인한 뒤 확정한다.
- 파일럿 평가지표는 최대 3개, 결과 표현은 Green/Yellow/Red로 단순화한다.
- 과거 일별 품절 이력이 없으므로 파일럿 시작 시점부터 동일 기준의 스냅샷을
  새로 쌓아야 한다.

### 2.2 아직 확정되지 않은 핵심 사항

- 본사에서는 `발주분석 V2(BETA)`만 진행하는 방향이나 최종 확정이 필요한지
- 본사 산식이 PL V2의 3개 레이어를 그대로 공유하는지
- 본사에서도 두 시나리오 `CASH`/`SHORTAGE`를 유지할지와 각각의 업무 의미
- 발주 또는 재검토 주기가 2주인지 4주인지
- 보호기간에 발주주기를 어떤 방식으로 반영할지
- 브랜드별 리드타임을 쓰면서 Pareto 80% 등급은 브랜드별로 계산할지,
  파일럿 전체 SKU 모집단에서 계산할지
- OPO 재고와 미입고를 V2의 네 재고 위치에 어떻게 매핑할지
- 미입고 수량을 전부 인정할지, ETA·상태·노후 건에 따라 제외할지
- OPO 창고 전체 판매를 국내 B2B 모집단으로 보는 방향은 잠정 확인됐으나,
  반품·취소·무상·샘플 등 판매행 인정 기준
- 부분입고가 있는 PO의 “실제 입고일”을 최초·최종·수량가중 중 무엇으로 볼지
- 12개월 관측창을 PO 생성일 기준 cohort로 잡을지, 입고 완료일 기준으로 잡을지
- 리드타임 일수를 달력일과 영업일 중 무엇으로 계산할지
- 브랜드별 리드타임의 최소 표본 수, 이상치 규칙, 표본 부족 처리
- 정상 운영 SKU, 단종·홀드·판매중지·세트 SKU의 포함 기준
- 실제 발주수량과 공급수량을 어디에 영속 기록할지
- 쇼티지 정의와 Green/Yellow/Red 수치 경계
- 파일럿 접근 계정과 대상 브랜드 제한
- 조회·설정변경·검토수량 입력·파일럿 확정 역할을 어떻게 분리할지

이 항목을 답하지 않은 상태에서 산식이나 기본값을 구현하지 않는다.

### 2.3 현재 범위 밖으로 분리할 항목

- CMS 구매요청 자동 전송 및 승인 워크플로
- 전 법인 공통 정책으로의 즉시 확대
- 과거 품절기간의 추정 복원
- 공급사 포털

위 항목은 별도 승인 없이 본사 조회 기능에 끼워 넣지 않는다.

| 시나리오 UI | CASH=철송, SHORTAGE=해운으로 설명 | 본사 업무 의미와 맞지 않음 |
| 금액 | API, 화면, Excel이 `unit_price_eur`, EUR/KRW를 사용 | HQ 원화 단가에 EUR 환산을 적용하면 안 됨 |
| Excel | EU창고·운송중·철송·해운·EUR 문구와 수식 사용 | 본사 전용 컬럼/통화 계약 필요 |
| 결과 식별 | result에 법인·창고가 없고 프런트 모델도 선택 법인을 의존성으로 쓰지 않음 | 법인 전환 시 이전 결과 혼입을 결과 자체로 검증하기 어려움 |
| 이력 저장 | latest snapshot은 클라이언트별 최신 1건 중심, job도 보존기간 후 정리 | 0주/2주/4주 파일럿 증빙 저장소로는 부족 |

`CMS_API_GUIDE.md`에도 현재 본사는 판매 분석만 제공하며 재고·미입고·운송 API가
없어 발주분석을 실행하지 않는다고 명시돼 있다. HQ API가 확정되면 코드와 함께
이 문서도 갱신해야 한다.

## 4. 놓치기 쉬운 위험과 방지 규칙

### R-01. 본사 화면에서 PL 데이터가 계산되는 위험 — 치명적

원인: V2 백엔드가 법인 코드를 background job과 원천 조회에 전달하지 않는다.

방지:

- `entity_code`, `warehouse_code`를 요청 시점에 서버가 확정한다.
- 둘을 job request, source snapshot, result, latest key, audit에 남긴다.
- HQ adapter가 없으면 계산을 차단한다.
- `HQ -> PL fallback 없음` 회귀 테스트가 통과하기 전 HQ 차단을 제거하지 않는다.

### R-02. 발주주기와 보호기간을 같은 값으로 오해하는 위험 — 치명적

현재 V2는 `P_weeks = (LT_days + 7) / 7`로 1주 검토주기를 포함한다. 예를 들어
브랜드 리드타임이 28일이면 현재 보호기간은 5주다. 본사 파일럿의 검토주기를
4주로 확정해 `LT + 28일`을 써야 한다면 보호기간은 8주가 된다. 커버 버퍼만
2주에서 4주로 바꾸는 것은 같은 변경이 아니다.

방지:

- 발주주기, 검토주기, 추가 커버를 각각 정의한다.
- 산식 변경 전 사용자가 숫자로 검산할 예시를 보고 승인한다.
- PL V2 기본 산식은 본사 결정을 이유로 바꾸지 않는다.

### R-03. OPO 국내 B2B가 아닌 판매가 수요에 섞이는 위험 — 높음

`/us/sales/history`는 본사 전체 창고 모집단이다. 현재 판매 인사이트에서는 HQ
원천을 API 정의 그대로 쓰고, 선택 창고는 조회 후 필터한다. 오포 국내 B2B
발주 수요는 별도의 모집단 계약이 필요하다. 반대로 기존 발주 전처리 경로는
USA 외 법인에 PL/EU 거래유형 필터를 적용하므로 HQ 거래가 전부 빠질 수도 있다.
사용자는 OPO 창고 전체를 보는 방향이라고 답했으므로 이를 잠정 모집단으로
기록하되, 판매행 상태 규칙을 확인하기 전 최종 필터 계약으로 확정하지 않는다.

방지:

- `whouse_nm=OPO` 외에 허용 `biz_type`, Site, 취소·샘플·반품 규칙을 명시한다.
- 필터 전후 행 수·수량·금액을 snapshot 메타데이터에 남긴다.
- API 원천, adapter 결과, 웹 91일 합계를 표본 SKU로 대조한다.

### R-04. 반품과 음수 판매를 조용히 바꾸는 위험 — 높음

전 법인·본사 공통 발주 정책은 `amount < 0 AND qty > 0` 행을 확인된 사고처리
조정으로 보고 발주 수요와 Pareto에서 제외한다. HQ 판매이력에 다른 형태의 반품
행이 있을 수 있으므로 단순 합산, 0 치환, 절댓값 처리 중 어느 것도 추가로
추정해서 적용하면 안 된다.

방지:

- CMS에서 정상 출고와 다른 반품 유형을 구분할 필드를 계약한다.
- 사용자가 승인한 공통 규칙으로 식별되지 않는 음수 행은 별도 검토 대상으로
  남기고 임의로 순수요에 포함하거나 제거하지 않는다.

### R-05. 미입고와 실입고를 중복 계산하는 위험 — 치명적

예를 들어 OPO 가용재고 100개에 미입고 50개를 더했는데, 그중 20개가 실제로
입고됐음에도 PO 잔량이 아직 갱신되지 않았다면 재고 위치를 150개로 보게 된다.
실제 의도에 맞는 값은 데이터 동기화 상태에 따라 130개일 수 있다.

방지:

- 미입고는 `발주량 - 유효 입고량 - 취소량` 계약으로 검증한다.
- PO line과 입고 line의 키, 취소·반전 처리, 원천 갱신시각을 확보한다.
- 같은 시점으로 정합성을 맞출 수 없으면 경고가 아니라 계산 차단 조건을 정한다.

### R-06. 부분입고 리드타임 왜곡 — 높음

한 PO가 여러 날짜에 나뉘어 들어오면 PO별 리드타임 하나를 어떤 날짜로 계산할지에
따라 평균과 표준편차가 크게 달라진다. 완료 PO만 사용하면 오래 열린 PO가
표본에서 빠지는 생존편향도 생긴다.

방지:

- 매칭 grain은 최소 `PO 번호 + PO line + SKU`로 정의한다.
- 최초입고, 최종입고, 수량가중 입고일 중 사용할 기준을 확정한다.
- 미완료 PO 수와 나이를 별도로 보고한다.
- 표본 수와 제외 건수를 브랜드별로 표시한다.

### R-07. 12개월 데이터가 없을 때 6개월이나 PL 값을 자동 적용하는 위험 — 높음

회의의 “6개월 임시 사용 가능”은 fallback 로직이 확정됐다는 뜻이 아니다.

방지:

- 12개월/6개월 선택, 최소 표본 수, 차단 조건을 사용자 결정으로 기록한다.
- PL 리드타임 또는 다른 브랜드 평균을 조용히 대체 적용하지 않는다.
- 적용값, 표본기간, 표본 수, 출처를 실행 snapshot에 남긴다.

### R-08. 원화에 EUR 환율을 다시 곱하는 위험 — 치명적

HQ 판매는 `amount_krw`가 원화다. 현 V2의 EUR 필드와 EUR/KRW 환산 경로를
재사용하면 금액이 크게 왜곡된다.

방지:

- 판매 Pareto에 쓰는 원화 매출과 발주금액에 쓰는 매입단가의 통화 계약을
  분리해 확정한다.
- 본사 발주금액을 원화로 표시하기로 결정하더라도, 원천 단가가 외화라면
  승인된 환율 경로를 거친다. 원천 통화를 확인하지 않고 환율을 1로 두지 않는다.
- 내부 필드를 `unit_price_eur`에 억지로 넣지 않는다.
- API·화면·Excel 모두 기존 금액 권한 정책을 유지한다.

### R-09. 법인 전환 시 이전 결과가 남는 위험 — 높음

현재 V2 프런트의 latest 로딩은 선택 법인을 직접 의존하지 않고, result에도
법인·창고가 없다.

방지:

- 법인/창고가 바뀌면 실행·로딩·선택·수정 상태를 초기화한다.
- 응답의 법인/창고와 현재 선택이 다르면 렌더링을 거부한다.
- PL과 HQ의 동시·교차 전환 테스트를 둔다.

### R-10. “추천량”과 “실제 발주량”을 증빙하지 못하는 위험 — 높음

파일럿 평가는 추천량, 담당자 확정량, 실제 PO량, 공급량, 실입고량을 연결해야
한다. 현재 latest 결과는 장기 이력이 아니며, V2 Excel에는 과거 결정에 따라
`확정수량(담당자 발주)` 컬럼을 넣지 않는다.

방지:

- 기존 V2 Excel 결정을 몰래 되돌리지 않는다.
- 파일럿 실행 ledger 또는 별도 평가 export의 필요 여부를 확정한다.
- 계산 snapshot과 실제 PO/입고 이벤트를 불변 ID로 연결한다.

### R-11. 공급 부족을 산식 실패로 오판하는 위험 — 높음

브랜드 공급 히팅률, 취소, 지연을 분리하지 않으면 쇼티지 결과만으로 산식을
평가할 수 없다.

방지:

- 요청량, 확정 공급량, 실제 입고량, 미공급 사유를 별도 기록한다.
- 공급사 원인 제외 규칙과 Green/Yellow/Red 경계는 파일럿 시작 전에 확정한다.
- 공급 히팅률이 높은 브랜드만으로 산식을 검증하면 산식 영향 분리는 쉬워지지만
  전 브랜드 확대 가능성을 과대평가하는 선택편향이 남는다고 결과에 명시한다.
- 4주 평가일까지 실입고가 끝나지 않은 PO는 성공·실패로 조기 판정하지 않는다.

### R-12. SKU 상태와 단위 불일치 — 높음

단종·판매중지·샘플·세트·리뉴얼 SKU가 섞이거나, 판매는 낱개인데 PO가 박스
단위면 제안량이 의미가 없다.

방지:

- SKU 운영상태와 단위/입수 변환 필드를 계약한다.
- 변환 근거가 없으면 모두 낱개라고 추정하지 않는다.
- SKU 코드 변경·합본 규칙이 없으면 이력을 합치지 않는다.

### R-13. 파일럿 스냅샷 시점이 서로 다른 위험 — 높음

재고, 판매, PO, 입고 API의 갱신 시각이 다르면 같은 “기준일”이어도 하나의
재고 위치가 아니다.

방지:

- HQ 기준 시간대를 명시적으로 확정한다. 회의 맥락상 `Asia/Seoul`이
  유력하지만 결정 로그에 기록되기 전에는 구현 기본값으로 넣지 않는다.
- 원천별 기준시각과 조회완료시각을 남긴다.
- 허용 가능한 원천 간 시차와 재조회/차단 기준을 확정한다.

### R-14. 기존 V2 설명과 코드의 불일치가 확대되는 위험 — 중간

현재 일부 수식 설명 UI에는 이미 제거된 MOQ 문구가 남아 있다. 본사 분기를
추가하면서 기존 모순을 복제하지 않는다.

방지:

- 산식 설명은 core와 승인 문서를 기준으로 한 곳에서 파생하도록 검토한다.
- PL/HQ 공통 문구와 법인별 문구를 분리해 테스트한다.

### R-15. 브랜드별 리드타임과 Pareto 모집단을 잘못 결합하는 위험 — 치명적

회의에서는 본사 리드타임을 브랜드별 PO·실입고 이력으로 계산하는 방향을
논의했다. 하지만 현재 core는 한 실행의 모든 SKU에 동일한 리드타임과
리드타임 시그마를 적용한다. 이를 피하려고 브랜드마다 core를 따로 실행하면
Pareto 80% 등급도 브랜드 안에서 다시 계산될 수 있어, 전체 모집단 기준 등급과
다른 Z값이 적용된다.

방지:

- 리드타임 통계의 grain과 Pareto 매출 모집단을 각각 확정한다.
- 사용자가 화면에서 브랜드를 필터링할 때 등급이 재계산되는지 여부를 확정한다.
- per-SKU/per-brand 적용값을 core 입력으로 전달할지, 승인된 그룹 실행을
  사용할지 설계한 뒤 PL 결과 불변 테스트를 둔다.
- 단순히 전체 브랜드 평균 리드타임을 새 기본값으로 넣지 않는다.

### R-16. 화면 시나리오와 Excel 시나리오가 달라지는 위험 — 높음

현재 V2는 화면에서 빠르게 시나리오를 바꿀 때 표시용 draft mode만 바뀔 수
있지만, Excel export 요청은 job ID와 행·담당자 입력만 보내 원 실행의 공식
mode를 내보낸다. 따라서 화면에서 현금흐름 우선을 보고 있다고 생각했는데
Excel은 쇼티지 방어 결과일 수 있다.

방지:

- HQ 시나리오를 유지한다면 현재 표시 mode, 공식 적용 mode, export mode를
  하나의 검증 가능한 계약으로 만든다.
- 설정 또는 적용 mode가 바뀌었으면 재계산 전 export를 차단한다.
- Excel 메타데이터와 행 수량을 화면의 공식 결과와 숫자로 대조한다.

### R-17. HQ 권한이 있는 모든 계정에 파일럿 기능이 열리는 위험 — 높음

현재 여러 팀 계정이 HQ 법인을 선택할 수 있고, 일반 발주 접근은 일부 계정을
제외하는 방식이다. HQ 선택 권한과 파일럿 발주 권한은 같은 의미가 아니다.

방지:

- 조회, 고급설정 변경, 담당자 수량 입력, 파일럿 확정, 향후 CMS 전송, 승인을
  각각 명시적 allowlist로 분리한다.
- PO·공급사 정보는 금액 마스킹만으로 충분한지 별도 보안 검토를 받는다.
- 파일럿 범위 밖 브랜드와 창고는 UI뿐 아니라 API에서 차단한다.

### R-18. 원천 조회 실패를 오래된 latest 결과로 숨기는 위험 — 치명적

기존 발주 준비 화면에는 새 CMS 분석이 실패하면 오류를 전면에 드러내지 않고
저장된 latest 결과를 다시 불러오는 경로가 있다. HQ에서는 재고나 PO 조회가
실패했는데도 사용자가 현재 분석으로 오인해 중복발주할 수 있다.

방지:

- HQ의 재고·PO·입고 핵심 원천 중 하나라도 실패하면 새 계산과 발주 확정을
  차단한다.
- 오래된 결과를 조회용으로 보여줄지는 별도로 결정하되, 기준시각·경과시간·
  실패 원천을 화면과 Excel에 명확히 표시한다.
- `stale` 허용시간, 부분 실패 허용 여부, 재시도와 수동 override 권한을
  구현 전에 확정한다.

## 5. 구현 전 인터뷰 의사결정

### 1차: 기능 경계

1. **잠정 결정:** 본사에서는 표준편차 기반 `발주분석 V2(BETA)`만 진행하고
   기존 `발주분석`은 계속 차단한다. 최종 승인 시 `확정`으로 바꾼다.
2. 파일럿 동안 모든 HQ 권한 사용자에게 보일지, 지정 계정·지정 브랜드에만
   보일지 확정한다.
3. 계산 결과를 참고용 shadow 제안으로만 쓸지, 실제 구매요청 판단까지 쓸지
   확정한다.

### 2차: 산식과 재고 위치

4. 본사에서도 현금흐름 우선/쇼티지 방어 두 시나리오를 유지할지 확정한다.
5. 발주주기, 검토주기, 추가 커버의 값을 각각 확정한다.
6. Pareto 80%를 브랜드별로 계산할지, 파일럿 전체 SKU에서 계산할지 확정한다.
7. OPO 가용재고, Hold, 미입고, 입고예정/이동중 수량을 재고 위치에 어떻게
   포함할지 확정한다.
8. 미입고 인정 제안수량과 미입고 제외 상한수량을 본사에서도 함께 보여줄지
   확정한다.

### 3차: 데이터와 리드타임

9. **잠정 결정:** 국내 B2B 모집단은 OPO 창고 전체 판매로 본다. 반품·취소·
   무상·샘플 등 판매행 인정 기준을 확인한 뒤 최종 확정한다.
10. 부분입고의 리드타임 종료일과 PO 취소·수정 처리 규칙을 확정한다.
11. 12개월 표본을 PO 생성일과 입고 완료일 중 어느 기준으로 포함할지,
    달력일/영업일 중 무엇을 쓸지 확정한다.
12. 브랜드별 최소 표본 수, 이상치 규칙, 12개월 부족 시 처리 방법을 확정한다.
13. 단종·홀드·신상품·세트 SKU 처리 규칙을 확정한다.
14. 매입단가의 원천 통화와 총 발주필요금액의 표시 통화·환율 기준을 확정한다.

### 4차: 파일럿 기록과 성공 기준

15. HQ 기준 시간대, 일별 스냅샷 시간과 보존 장소/기간을 확정한다.
16. 추천량과 실제 발주량을 연결할 기록 방식을 확정한다.
17. 공급 히팅률 산식과 공급 부족 제외 규칙을 확정한다.
18. 최대 3개 평가지표와 각 Green/Yellow/Red 수치 경계를 확정한다.

각 답변은 이 문서의 결정 로그에 날짜, 결정자, 근거와 함께 기록한다.

## 6. HQ/OPO API 계약 초안

아래는 필드명을 확정한 기술명세가 아니라, MCP 또는 CMS 담당자와 실제 컬럼을
확인할 때 빠뜨리지 않기 위한 체크리스트다. 실제 컬럼명과 코드값을 확인하기
전에는 endpoint나 매핑을 구현하지 않는다.

### 6.1 모든 원천에 필요한 공통 메타데이터

| 항목 | 목적 |
| --- | --- |
| `entity_code=HQ` | 법인 혼입 방지 |
| `warehouse_code=OPO` | 물리·업무 범위 고정 |
| 원천 기준시각과 시간대 | 동일 snapshot 여부 판단 |
| 조회 조건과 페이지 정보 | 재현성과 누락 검증 |
| 원천별 행 수·수량 합계 | CMS/API/Web 3단 대조 |
| 통화와 수량 단위 | 환산·입수 오류 방지 |
| source version 또는 schema version | CMS 클렌징 변경 감지 |
| 원천 레코드의 안정적인 고유 키 | 페이지 중복·수정·재조회 판별 |
| 원천 추출 hash | 파일럿 결과 재현과 변조·혼입 감지 |

### 6.2 판매이력

- 고유 판매 line ID 또는 중복 판별 키
- 출고일시
- SKU, 상품명, 브랜드
- 창고 코드
- 거래유형, Site, 주문/송장 상태
- 판매수량과 단위
- 원화 금액
- 반품·취소·무상 샘플 구분
- 원거래 ID와 수정시각

### 6.3 OPO 재고 snapshot

- 기준일시
- SKU, 브랜드
- 총재고, Hold, 가용재고
- 재고 상태와 SKU 운영상태
- 평균 매입단가와 통화
- 수량 단위

`가용재고 = 총재고 - Hold`가 항상 성립하는지 표본 대조가 필요하다. API가
가용재고를 직접 제공하면 웹에서 임의 재계산해 원천값을 덮어쓰지 않는다.

### 6.4 미입고/구매오더

- PO 번호와 PO line 번호
- line revision 또는 수정 이력 키
- PO 생성일시
- SKU, 브랜드, 공급사
- 발주수량, 취소수량, 유효 발주수량
- 입고누계, 미입고 잔량
- 예정 입고일
- PO/line 상태
- 단가, 통화, 수량 단위

현재 PL/USA `open-po`의 SKU 집계형 필드만으로는 본사 리드타임과 부분입고를
검증하기 어렵다.

### 6.5 실제 입고이력

- 입고 이벤트 ID
- 연결 PO 번호와 line 번호
- SKU
- 실제 입고일시
- 입고수량
- 입고 창고
- 취소·반전·검수 상태
- 원천 수정시각

PO와 입고를 SKU만으로 연결하지 않는다. 동일 SKU가 여러 PO에 존재하면
리드타임과 히팅률이 잘못 매칭된다.

### 6.6 상품마스터

- SKU와 바코드
- 브랜드와 공급사
- 정상판매/단종/홀드/판매중지 상태
- 세트·구성품·리뉴얼 관계
- 기본 수량 단위와 입수

## 7. 제안하는 코드 경계

확정된 HQ 산식이 기존 V2 core와 호환되는 경우에도 PL source adapter를
분기문으로 계속 늘리지 않는다.

```text
HTTP request
  -> 서버가 권한 있는 entity/warehouse 확정
  -> entity-specific source adapter
       PL: 기존 6개 CMS 원천
       HQ: OPO 판매·재고·PO·입고 원천
  -> generic immutable calculation snapshot
  -> entity/policy configuration snapshot
  -> pure calculation core
  -> entity-aware response / UI / Excel
```

필수 불변조건:

- source adapter는 원천 의미만 변환하고 승인되지 않은 산식을 계산하지 않는다.
- core 변경은 PL 회귀 결과를 바꾸지 않아야 한다.
- 법인별 설정이 없으면 계산을 차단한다.
- result에는 `entity_code`, `warehouse_code`, `timezone`, `currency_code`,
  원천 snapshot ID, 정책 version, 리드타임 표본기간·표본 수를 남긴다.
- 화면은 result의 법인/창고가 현재 선택과 다르면 결과를 표시하지 않는다.
- HQ 단가·금액은 기존 금액 권한을 통과한다.

## 8. 구현 및 릴리스 게이트

### Gate A. 결정 완료

- 1차~3차 인터뷰 질문이 결정 로그에 기록됨
- 산식 변경 계획과 손검산 예시를 사용자가 승인함

### Gate B. API 원천 검증

- 필요한 원천 endpoint와 필드 명세 확보
- OPO/국내 B2B 필터 코드 확인
- CMS 화면 또는 원본 추출과 API의 표본 건·합계 대조
- PO line과 입고 line 매칭률, 미매칭 사유 확인
- 12개월 리드타임 표본 가용성 확인

### Gate C. shadow 계산

- 실제 구매요청과 연결하지 않은 상태로 계산
- HQ가 PL cache·정책·환율을 사용하지 않는 테스트 통과
- 계산불가/누락/음수/부분입고/표본부족 상태가 숨겨지지 않음

### Gate D. 파일럿

- 최종 브랜드와 SKU 범위 확정
- 0주차 기준 snapshot 저장
- 추천량·실제 발주량 ledger 연결
- 2주차 중간점검과 4주차 최종점검 일정 확정

### Gate E. 확대

- 공급 부족을 분리한 결과 평가
- 쇼티지 감소와 재고 부담을 함께 검증
- 승인 후에만 대상 브랜드·계정·법인 범위를 확대

## 9. 필수 테스트 목록

### 권한과 법인 격리

- HQ 요청이 PL 또는 USA **현지 발주** endpoint를 호출하지 않음
  (`/us/sales/history`처럼 계약상 HQ 원천인 경로는 명시적 allowlist로 구분)
- HQ 정책이 없으면 409로 차단
- 허용되지 않은 계정/브랜드/창고 접근 차단
- 조회/설정/검토/확정 역할별 권한 차단
- 금액 권한이 없으면 API·화면·Excel 모두 단가·금액 제거

### 원천과 필터

- OPO 외 창고 제외
- 승인된 국내 B2B 거래만 포함
- 중복 판매 line 제거 또는 차단
- 반품·취소·샘플 규칙
- 원천별 stale/부분 실패 시 계산 차단

### PO와 입고

- 한 PO 한 번 입고
- 부분입고 여러 번
- PO 수량 수정·취소
- 입고 반전
- 동시에 열린 동일 SKU의 여러 PO
- PO/입고 미매칭
- 미입고 잔량과 재고의 갱신시각 불일치

### 산식

- 정확히 91개 완료일
- 판매없는 주의 0 처리와 원천 누락 주의 구분
- 표본부족 브랜드 리드타임
- 2주/4주 검토주기별 승인 예시
- 미입고 인정/제외 수량
- 정수 올림과 음수 입력
- 공통 `amount < 0 AND qty > 0` 사고처리 제외 규칙과 HQ 결과의 일관성

### UI와 내보내기

- HQ/PL 전환 직후 이전 결과가 보이지 않음
- 결정 로그에 승인된 HQ 시간대 기준일
- KRW 표기와 환율 미적용
- HQ에 EU/철송/해운 문구가 남지 않음
- snapshot ID와 기준시점 표시
- 법인/창고가 다른 latest 결과 재사용 거부
- 화면의 공식 적용 시나리오와 Excel의 적용 시나리오·수량 일치

### 파일럿 증빙

- 0주/2주/4주 snapshot 불변 저장
- 추천량, 담당자 결정량, 실제 PO량, 공급량, 실입고량 연결
- 계산 version과 적용 리드타임 통계 재현
- Green/Yellow/Red 경계값 테스트

- 라우터 `409` 차단 해제 후에도 미연동 법인(`UK/ME/MX/MY/VN`)은 계속 차단한다.
- PL/USA 원천·통화·정책은 변경하지 않았고 기존 회귀 테스트는 그대로 통과한다.
- 대량포함 판정 기준 변경(HQ-016)은 `core/order_logic_v2.py::calculate_hq_sku_order`의
  품질 판정에만 적용했고 `S`·`Q` 산식은 바꾸지 않았다. 판매일수가 3일 이하인
  SKU는 새 기준에서 대량포함이 성립할 수 없으나, 이들은 모두 간헐 판정으로
  검토 대상에 남는다.
- 간헐 판정 제외(HQ-017) 이후에는 위의 보완 설명이 성립하지 않는다. HQ에서
  판매일수가 적은 SKU는 `정상`으로 분류되므로, 소량·비정기 조달 SKU가 별도
  경고 없이 발주 제안에 포함된다. 필요하면 판매일수 자체를 화면·Excel의 참고
  열로 노출하는 방안을 별도 결정한다.
- 파일럿 게이트(Gate D·E)와 평가지표 경계(HQ-005, HQ-009)는 여전히 미결이다.

## 11. 작업 보고 규칙

본사 발주분석 변경을 보고할 때는 최소 다음을 포함한다.

1. 이번 변경이 원천 매핑, 산식, 정책, 표시, 파일럿 기록 중 어디인지
2. 공통 사고처리 제외 규칙을 적용한 범위와 기존 산식에 영향이 없는 범위
3. 사용한 법인·창고·시간대·통화
4. API 원천과 웹 결과의 표본 숫자 대조
5. 계산 예시 1~2개
6. 실행한 테스트와 미검증 항목
7. 임시값이나 fallback이 있다면 승인된 근거

테스트 통과만으로 수량·금액의 정합성이 입증됐다고 표현하지 않는다.
