# 전사 재고 현황 탭 - 작업 기록과 결정 로그

> 상태: 보유재고·운송중 원천 및 화면 구현 완료, 실제 운영 데이터 대기.
> 마지막 갱신: 2026-08-25

> 운송중 계약환율과 원화 합산의 공통 기준은
> [`KRW_CONVERSION_HANDOFF.md`](KRW_CONVERSION_HANDOFF.md)를 따른다.

## 1. 화면 목표

사용자명 `adminmaster`만 전사 재고 금액을 다음 계층으로 탐색한다.

```text
전사 총 재고 규모
├─ 보유 재고 금액
│  └─ 법인(Site)별 금액
│     └─ 창고별 금액
└─ 운송중 재고 금액
   └─ 도착 법인별 금액
      └─ 운송수단별 금액 (원천과 판별 규칙이 확정된 경우에만 표시)
```

초기 화면은 전사 합계와 두 분류(보유/운송중)를 보여 주고, 카드 또는 행 클릭으로 한 단계씩 상세를 연다. UI는 기존 `SiliconAnalyticsWorkspace`의 좌측 내비게이션, 상단 헤더, 표면 색상, 카드, 테이블, 모바일 메뉴 규칙을 재사용한다.

## 2. 현재 확인된 사실

### 권한

- 로그인 세션은 백엔드의 HttpOnly 쿠키가 소유한다. 프런트에서 메뉴를 숨기는 것만으로는 권한 보호가 되지 않는다.
- 이 탭은 `MASTER` 역할 전체가 아니라 **사용자명 `adminmaster` 한 계정**만 허용한다.
- 기존 금액 열람 권한은 `adminmaster`, `ia`에 열려 있다. 따라서 이 탭은 그 정책을 재사용하면 안 되며, **`adminmaster` 단독 서버 권한 검사**가 필요하다.
- 화면 경로 직접 입력, API 직접 호출, 이전 계정의 브라우저 캐시/탭 복구 모두 403 또는 비노출로 막아야 한다.

### 기존 앱 구조

- 앱 루트: `ESM_SCM8/`
- 워크스페이스 화면 식별자와 경로: `frontend/components/redesign/lib/types.ts`, `workspace-routes.ts`
- 좌측 메뉴 및 화면 분기: `frontend/components/redesign/SiliconAnalyticsWorkspace.tsx`
- 인증/법인 권한: `backend/services/auth.py`, `backend/auth/permissions.py`, `frontend/components/auth/AuthGuard.tsx`
- 금액 데이터 마스킹: `backend/auth/amount_permissions.py`
- 기존 CMS 연동은 EU·USA 중심이다. 전사 보유 재고(모든 법인·창고)를 합치는 전용 API 계약은 현재 확인되지 않았다.

### 2026-08-20 CMS OpenAPI 대조 결과

- 공개 OpenAPI의 `GET /api/v1/esm/stock-ledger`는 모든 법인을 법인 → 창고 구조로 반환한다. 보유재고 금액은 **법인 `eqty_cost`(기말 재고금액, KRW)**를 사용하기로 확정했다. 기준일은 오늘 KST이며, API의 필수 `start_date`와 `end_date`에 같은 날짜를 보낸다. 창고 `eqty_cost`는 법인 합계에 더하지 않고 상세 표시에만 사용한다.
- `GET /api/v1/esm/in-transit`는 목적지 법인·운송수단·거래통화 금액·수량을 준다. 2026-08-20 사용자 확인으로 이 API의 반환 범위는 **본사(HQ) → 해외 법인 출발분 전체**다. 인보이스 번호·비고 등 원문은 서버에서 통화별 합계를 만들 때만 사용하고 브라우저·로그·저장소로 보내지 않는다.
- 운송중 금액은 `/esm/in-transit`의 `amount_krw`를 그대로 사용한다. 이 값은 인보이스에 기록된 계약환율이며 `xrate_source=INVOICE`로 검증한다.
- 본사 OPO 단일 창고 재고는 `GET /api/v1/opo/inventory`에서 SKU 단위로 제공한다. 이는 전사 집계용이 아니라 OPO 상세·대사용 후보이며, 단가 0 수량과 불량 재고 상태가 별도 필드로 존재한다.
- 네트워크/외부 API 오류는 실제로 발생할 수 있다. 기존 CMS 연동 가이드는 간헐적인 502/timeout과 2~3회 재시도를 명시한다. 따라서 API 조회 실패를 0원으로 바꾸지 않고 ‘갱신 실패’로 표시한다.
- API 명세의 금액 의미: `sqty_cost`는 기초 재고금액, `qty_plus_cost`는 입고금액, `qty_minus_cost`는 출고금액(음수), `eqty_cost`는 **조회 종료일의 기말 재고금액**이다. 사용자 결정에 따라 이 기능의 ‘현재 보유재고 금액’에는 법인 `eqty_cost`를 사용한다.

### 첨부된 운송중 재고 기술자료에서 확인한 제약

- 운송중 여부는 `TB_PNFM.close_yn = 'N' AND TB_PNFM.iw_yn = 'N'` 같은 **상태 필드**로 판정해야 한다. 운송수단 텍스트로 운송중 여부를 추정하지 않는다.
- 목적지 법인 기준은 `TB_PNFM.comp_cd`가 우선이다. `whouse_cd`는 목적지 판정 필터가 아니라 검증 보조값이다.
- 인보이스에 같은 SKU가 여러 줄이면 SKU 단순 조인으로 수량·금액이 중복 집계될 수 있다. 문서의 `EXISTS` 방식은 과대 집계를 완화하지만 인보이스 라인 단위 완전 매칭은 스키마상 불가능하다고 명시되어 있다.
- `ship_dt`가 비어 있는 사례가 있어, 운송중 자료의 기간/노후 기준으로 사용할 날짜 필드는 AX·CA 확인이 필요하다.
- KRW 환산은 당시 미결이었으나, 2026-08-24 배포로 아래 D-04의 인보이스 계약환율 기준으로 갱신됐다.
- 목적지별 운송수단 판별 원천은 법인마다 다를 수 있다. EU 예시는 `remark`, 다른 목적지는 미확정이다.
- 제안된 API 경로(`/inventory/summary`, `/inventory/in-transit`)는 예시이며 실제 서비스 경로가 확정된 것은 아니다.

## 4. 알려진 위험요소와 방어 원칙

1. **보유 재고와 운송중 재고의 중복**: 입고완료 또는 이미 창고 재고에 반영된 건을 운송중에도 넣으면 총액이 과대 집계된다. 두 집계의 배타적 상태 정의를 API 계약과 테스트에 고정한다.
2. **통화 혼합**: 법인 원화 환산값을 단순 합산하면 환율 기준이 달라진다. 응답에는 `as_of`, 원통화 합계, 환율 원천/일자, KRW 합계를 함께 남긴다.
3. **불완전한 전사 범위**: 응답 누락을 0원으로 표시하지 않는다. 법인별 `available / unavailable / stale` 상태와 제외 사유를 화면에 명시한다.
4. **운송중 중복 조인**: 집계 SQL/API에 집계 단위, 중복 제거 방식, 알려진 잔여 오차를 메타데이터로 반환한다. 원천의 한계는 UI에서 숨기지 않는다.
5. **권한 우회**: 메뉴 숨김은 편의 기능일 뿐 보안 통제가 아니다. 프런트 메뉴·경로 가드, 서버 API 의존성, 금액 응답 마스킹, 테스트를 모두 적용한다.
6. **스냅샷 불일치**: 법인별 조회 시각이 다르면 전사 합계가 실제 동일 시점 재고가 아니다. 스냅샷 기준시각과 부분 실패를 표시하고, 가능한 경우 서버에서 한 번에 집계한다.
7. **성능/외부 의존성**: 각 법인·창고·운송 데이터를 화면 진입 때 연쇄 호출하면 느리고 실패율이 커진다. 서버 집계, 타임아웃, 캐시 TTL, 재시도·관측 항목을 API 계약에 포함한다.

## 5. 프로젝트 작업 규칙

- 실제 앱 코드만 `ESM_SCM8/` 아래에서 수정한다.
- 기존 사용자 변경을 덮어쓰거나 이번 기능과 관계없는 파일을 정리하지 않는다.
- 금액/수량 산식은 기술명세 없이 추정하지 않는다. 확정된 산식은 구현 전 자연어와 손검산 예시로 설명하고 승인을 받는다.
- 권한은 프런트와 백엔드에서 모두 검증한다. 민감 금액을 브라우저 저장소, 로그, fixture, 문서에 쓰지 않는다.
- 신규 API는 기존 발주분석 및 V2의 코드 경계를 건드리지 않는다.
- API 응답에는 기준시각, 데이터 범위, 누락/경고 상태를 포함한다. 운송중 응답에는 원통화 금액, KRW 환산액, 고시통화 단위와 고시일만 포함하고 인보이스 원문은 포함하지 않는다.
- 테스트는 최소한 역할별 API 200/403, 직접 경로 진입 차단, 합계=세부합계, 환율/반올림, 중복 방지, 부분 실패 표시를 포함한다.

## 6. 화면 구성 추천

- 좌측 메뉴 최상단에 새 그룹 **`경영 · OVERVIEW`** 를 만들고, 첫 항목을 **`전사 재고 현황`** 으로 둔다.
- `발주 · QUANTITATIVE`보다 위에 둔다. 이 화면은 발주를 실행하는 작업 화면이 아니라 전사 규모를 파악하는 경영 현황 화면이기 때문이다.
- `adminmaster`가 아닌 사용자는 메뉴, 즐겨찾기, 모바일 메뉴, 직접 URL 모두에서 이 항목을 볼 수 없으며 API도 403이어야 한다.
- 첫 화면은 전사 총액 / 보유재고 / 운송중재고 카드, 법인별 보유재고 표, 운송중 도착 법인 표, 기준시각·집계 실패 상태를 사용한다. 법인 행 클릭은 창고별 표만 연다.

## 8. 계정 설정 메모

- 2026-08-20 확인 결과, 과거 테스트용으로 추가됐던 보조 MASTER·관리자 계정은 소유자 동의에 따라 애플리케이션 계정 목록과 개발용 환경변수 예시에서 제거했다.
- 기존 금액 열람 정책의 `ia`는 `INTERNAL_AUDIT` 역할이다. 따라서 역할·관리자 플래그·금액권한은 서로 같지 않다. 이번 화면은 역할이나 `is_admin`을 재사용하지 않고 **사용자명 `adminmaster`만 허용**한다.
- 배포 비밀 저장소에는 과거 계정용 해시 키가 남아 있을 수 있다. 애플리케이션에 그 키를 읽는 계정 정의가 없으므로 로그인에는 사용할 수 없지만, Secret 템플릿을 변경하면 다른 로그인 해시를 재생성할 위험이 명시돼 있다. 배포 후 운영 비밀 관리 절차로 별도 정리한다.

## 9. 1차 구현 기록

### 반영 범위

- 메뉴 경로: `경영 · OVERVIEW` → `전사 재고 현황` (`/overview/inventory`)
- 서버 API: `GET /api/corporate-inventory`
- 보유재고 원천: `GET /esm/stock-ledger`에 오늘 KST를 `start_date`와 `end_date`로 동일하게 전달한다.
- 집계: 법인 `eqty_cost`만 합산한다. 창고 `eqty_cost`는 법인 클릭 후 상세 표시에만 사용한다.
  - 손검산 예시: PL 법인 10억(창고 6억+4억), USA 법인 20억이면 전사 보유재고는 **10억+20억=30억**이다. 하위 창고 30억을 다시 더하지 않는다.
- 법인별 순위 막대: `법인 보유재고 ÷ 전사 보유재고 × 100`으로 비중을 표시한다.
  - 손검산 예시: 법인 보유재고 10억, 전사 보유재고 30억이면 **10 ÷ 30 × 100 = 33.3%**다.
- 오류: 재고수불부가 실패하거나 `eqty_cost`가 비어 있으면 합계를 0원으로 만들지 않고 **`갱신 실패`**를 반환·표시한다.
- 권한: 프런트 메뉴/직접 경로와 서버 API 모두 사용자명 `adminmaster`만 허용한다. `ia`, `is_admin`, 금액 열람 권한은 허용 근거가 아니다.
- 운송중: `esm/in-transit`에서 목적지별 인보이스의 `amount_krw`를 합산한다. 외화는 인보이스 계약환율(`INVOICE`)이 이미 반영돼 있으므로 재환산하지 않는다.
- 총 재고 규모: 보유재고와 운송중 재고가 **모두** `ready`일 때만 두 KRW 합계를 더한다. 하나라도 금액·통화·환율·원천 조회에 실패하면 운송중은 `갱신 실패`, 총 재고는 `산출 불가`로 표시하며 부분 합계나 0원으로 대체하지 않는다.

## 10. 운송중 환산 구현 결정

- 조회: `GET /esm/in-transit?start_date=2026-01-01&end_date={오늘 KST}&biz_gbn=ALL`. 여기서 종료일은 **패킹일 종료 필터**이며 도착예정일이 아니다. `ALL`은 COSMETIC과 KPOP을 모두 조회하며, 혼합 인보이스는 사업군별 행을 중복 제거하지 않고 모두 합산한다.
- 집계 단위: `도착 법인 → 거래통화`. 한 법인에 EUR·USD 등이 함께 있어도 서로 먼저 더하지 않고 각각 원화로 환산한 뒤 합친다.
- 환산: API의 `amount_krw`를 사용하며 외화 행은 `xrate_source=INVOICE`, `xrate`, `xrate_dt`가 있어야 한다.
- 실패: `biz_gbn`이 COSMETIC/KPOP이 아니거나, 금액·수량·통화가 비어 있거나, 외화 행의 계약환율 근거가 없으면 운송중 전체를 실패 처리한다.
- 화면: 카드에는 KRW 운송중 합계, 하단에는 도착 법인별 원통화 금액·KRW 환산액·계약환율·기준일을 표시한다. KRW 건은 `환산 없음`으로 보인다.
