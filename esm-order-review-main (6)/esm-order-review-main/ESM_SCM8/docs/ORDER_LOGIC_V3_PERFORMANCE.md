# HQ 오포 발주분석 V3 성능 개선 — 2026-08-31

## 결과와 측정 범위

동일 저장 자료를 재생했을 때 데이터 가공·계산 시간이 **69.670초 → 30.175초**로
약 57% 줄었다. 이는 **CMS 새 조회·결과 저장·브라우저 표시를 제외한 단일 비교 측정**이며,
현재 날짜의 2년치 전체 분석이 30초에 완료된다는 의미가 아니다.

| 구간 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 원천 자료 → SKU 계산 입력 | 25.469초 | 11.522초 |
| 입력 변환 + 두 시나리오 계산 | 44.201초 | 18.653초 |
| 합계 | 69.670초 | 30.175초 |

- 기준 자료: 기존 2026-08-26 HQ 원천 스냅샷. 판매 207,390행, 상품 81,062행,
  재고 46,553행. 결과 모집단은 46,956 SKU.
- 두 실행 모두 분석 기준일을 2026-08-31로 고정했다. 최신 원천을 새로 받은 결과가 아니다.
- 모든 SKU 계산 입력, 대표 결과행, CASH/SHORTAGE 전체 결과를 정규화한 SHA-256이
  변경 전후 각각 일치했다. 금액·수량 일부만 표본 비교한 것이 아니다.
- 실행 당시 메모리 경합이 있었고, 같은 프로세스 재실행 시 메모리 부족이 발생하여
  변경 후 실행은 별도 프로세스로 수행했다. 반복 실험의 중앙값이나 보장 성능이 아니다.
- 측정용 코드와 출력에는 실제 CMS 행을 새로 저장하지 않았다.

## 확인된 병목

HQ V3는 기존에도 오포 수요 필터와 오포 재고 API를 사용한다. 다만 판매 API
`/us/sales/history`에는 확인한 OpenAPI 기준 창고 필터가 없어서, 약 2년치 HQ 이력을
받은 뒤 오포 수요를 추린다. 타 창고의 상품코드·이름 충돌도 상품 식별 근거로 사용하므로
원천에서 임의로 없애면 안 된다.

실제 기존 전체 기간 요청에서는 판매 페이지당 약 17~44초가 관측됐다. 별도 최소 행
조회도 40초 제한시간을 넘겼다. 전체 CMS 조회 완료시간은 측정하지 않았으며,
추가 부하를 줄이기 위해 진단용 전체 조회 프로세스만 중단했다.

기존 월별 캐시 24개에는 1,737,679행이 있었지만 HQ V3의 일괄 스냅샷 경로에서는
재사용하지 않았다. 해당 파일의 순차 읽기와 전표 순서 검사에는 총 8.155초가 걸렸다.
이 수치는 전체 V3 실행시간이 아니며, 미완료 월의 새 API 조회도 포함하지 않는다.

## 변경 사항과 보존 조건

1. V3 전용 `order_logic_v3_hq_fetch.py`에서 기존 월별 판매·상품 캐시를 재사용한다.
   오포 재고·미입고 PO·입고 확정·리드타임은 별도 캐시로 병렬 조회한다.
   V2의 일괄 원천 캐시와 키를 분리했으며 V2 조회 구현은 변경하지 않았다.
2. 판매 조회 기간은 줄이지 않는다. 기존 상품 식별, 최초 유상판매일, 오포 수요 필터,
   SKU 모집단, 승인된 시즌팩터와 발주 산식은 유지한다.
3. 실제 기존 피드의 전표번호 오름차순을 월별 합성 후 복원한다. 전표 내 행 순서와
   중복 행은 보존한다. 기존 207,390행의 월 분할·재합성 결과는 원본 순서와 같았고,
   24개 캐시에서 월 내 정렬 오류와 동일 전표의 월 경계 분할은 관측되지 않았다.
   전표 누락·월 내 역순·월 경계 분할 또는 월별 클라이언트의 잘못된 날짜 제거가
   확인되면 **기존 전체 기간 API 조회**로 되돌아간다. 새로운 수요 fallback은 아니다.
4. 오포 수요 필터를 행 복사보다 먼저 적용하되 상품 식별기는 모든 원천 증거를 본다.
   동일 HQ 판매 리스트를 상품 식별기에 두 번 전달하던 중복 작업을 제거한다.
5. SKU마다 DataFrame을 만드는 작업을 마지막 실제 행 선택으로 대체한다.
   판매 없는 SKU의 동일한 참고 판매이력은 기존 함수로 한 번 계산하고 개별 복사한다.
   계산식과 NULL 처리, SKU 간 변경 가능한 리스트의 독립성은 유지한다.
6. 원천 단계별 시간은 `source_audit.performance_seconds`, 작업 단계별 시간은
   결과의 `performance_seconds`와 `[perf][order_logic_v3]` 로그에 남긴다.
   `source`에는 API 조회가 포함되고, `calculation`과 `input_conversion`은 분리된다.

월별 캐시는 기존 공통 정책을 따른다. 완료 월은 만료시간 없이 재사용하고, 당월·상품·
현재 재고는 당일 캐시 TTL(기본 4시간)을 사용한다. 과거 판매가 사후 정정되었다면
`force_refresh=true`로 판매·상품·재고를 다시 받아야 한다. 조회 시각과 캐시 적중 여부는
원천 감사 메타데이터에 보존한다. 새 조회와 예전 캐시의 최신성이 같다고 가정하지 않는다.

## 연결 끊김 후속 개선 — 결과 분할 전송

### 관측 사실과 구분

- 기존 로그에서 47,071 SKU 계산 후 완료 상태 응답에 27.686초가 걸렸고,
  같은 작업 요청의 프런트 프록시에는 `socket hang up / ECONNRESET`이 남았다.
  기존 응답은 대표 결과·CASH·SHORTAGE 전체 배열을 한 번에 전달했다.
- 이후 점검 중 백엔드 PID가 바뀌었고 프런트에는 `ECONNREFUSED`도 기록됐다.
  이는 큰 결과 수신 도중 연결 종료와 별개인 서버 재시작/접속 불가 경로다.
  로그만으로 사용자가 겪은 모든 끊김의 원인이 같다고 단정하지 않는다.

### 구현

- 상태 조회는 `include_result=false`로 결과 본문을 읽거나 복사하지 않는다.
  DB 모드도 상태 조회 SQL에서 `result_payload`를 제외한다.
- 완료 결과는 `/jobs/{job_id}/result?offset=...`에서 최대 250행씩 받는다.
  이는 전송 단위이며 분석 모집단·계산 범위를 줄이는 필터가 아니다.
  JSON 직렬화와 페이지 복사는 작업 스레드에서 수행한다.
- 대표 결과가 시나리오 배열과 **같은 객체**일 때만 배열 별칭을 보내 중복 전송을
  제거한다. 값이 비슷하다는 이유로 SKU를 병합하거나 결과를 생략하지 않는다.
- 작업·법인·스냅샷·전체 행 수·페이지 범위를 검증하고 모두 받은 뒤 화면에 반영한다.
  금액 권한과 사용자/브라우저/법인 소유권 검사는 모든 페이지에 적용한다.
- 연결 오류·일시적 5xx·30초 응답 지연은 같은 페이지를 재시도한다. HTTP 헤더 수신
  이후 JSON 본문 읽기 중 끊김도 재시도 대상이다. 사용자 취소와 권한 오류는 구분한다.
- 재시도가 소진돼도 화면에서 별도 `분석 이어받기` 동작을 요구하지 않는다. 클라이언트가
  **같은 작업**에 자동으로 다시 연결하며 계산 POST를 다시 보내지 않는다. 결과 수신은
  첫 페이지부터 검증해 다시 받고, 수신 진척과 이전 완료 결과는 화면에 유지한다.
- 기존 클라이언트용 전체 결과 상태 API는 호환 목적으로 유지한다.

## Excel 내보내기 후속 개선 — 2026-08-31

변경 범위는 파일 생성·전달이다. HQ/OPO의 원천 필터, 수량·금액 산식, 시즌팩터,
시나리오 계산, 보류/차단 판정은 변경하지 않았다. PL/USA도 동일한 기존 Excel
매핑을 사용하며 새 수요·운송 fallback은 추가하지 않았다.

### 병목과 변경

- 기존 화면은 ExcelJS 문서형 workbook에 모든 셀과 서식을 넣은 뒤 전체 XML/ZIP을
  브라우저에서 생성했다. 확인필요 상품 40,423건은 숨김 `_계산기준`에도 모두 들어가므로
  수백만 셀을 한꺼번에 보관하게 된다. 실제 PC 로그에는 Turbopack의 시스템 자원 부족
  오류도 남았지만, 그 오류의 원인을 Excel 하나로만 단정하지 않는다.
- 브라우저는 새 동일 출처 `POST /api/order-v3-excel`에 실행 ID·스냅샷 ID·법인·시나리오·
  선택 SKU·담당자 검토값만 보낸다. 분석 결과 전체나 클라이언트 금액 권한을 보내지 않는다.
- Next 서버가 기존 백엔드의 인증/소유권/금액 권한을 적용한 결과 페이지를 읽는다.
  선택 시나리오의 요청 SKU만 보관하며 작업 ID·법인·스냅샷·행 수·중복·누락을 검증한다.
  `/auth/me`의 서버 권한으로 금액 표시를 결정한다. 재계산 POST는 발생하지 않는다.
- 기존 `populateV3Excel`의 동일 매핑을 generator로 공유한다. ExcelJS streaming writer가
  완성된 행을 즉시 파일에 기록하고 메모리에서 해제한다. 250행마다 이벤트 루프에
  제어를 돌려 압축·다른 HTTP 요청·취소가 처리되게 한다.
- 동일 서식 객체를 재사용한다. 워크시트 구성/열 너비/숫자 표시/주석/숨김 열과 시트/
  인쇄 설정/조건부 서식/필터를 유지한다. 공유 문자열을 사용해 빈 문자열과 NULL도
  기존 파일처럼 구분한다. ZIP 압축 수준 1로 생성 시간을 줄여 파일은 다소 커질 수 있다.
- 브라우저는 ZIP을 받으며 진행 용량을 표시한다. 진행 갱신은 250ms 간격으로 제한해
  수만 SKU 검토 화면을 ZIP 조각마다 다시 렌더링하지 않는다. 법인 전환/화면 이탈은
  다운로드와 서버 생성을 중단한다. 서버 프로세스당 동시 생성은 1개로 제한한다.
