# 발주분석 V3 시즌팩터 운영·계산 명세

## 수불 갱신 실패 수정 (2026-09-08)

- USA 갱신이 특정 월의 `OUT-SALE (ONLINE)` 입고 전용 행에서
  `LedgerSourceError`로 중단되는 것을 재현했다. 페이지 수집은 성공했으나
  판매 구분의 `qty_in > 0`을 일괄 차단하던 추가 검증이 원인이었다.
- 기존 승인된 `qty_out` 합계·0 출고 미기여 계약을 그대로 적용한다.
  `qty > 0`, `qty_in = qty`, `qty_out = 0`인 판매 구분 행은 판매에 0을
  기여한다. 입고수량을 판매에서 차감하거나 반품·취소로 추정하지 않는다.
  법인·창고·사업군·날짜·정수·부호·동시 입출고·페이지 완전성 검증은 유지한다.
- 합성 검산: 일반출고 32 + 온라인출고 3 + 입고 5/출고 0 = 판매 35.
  월 집계 감사의 `sales_inbound_only_row_count`에 해당 행 건수만 남긴다.
  계절지수 산식·판매 포함 구분·기존 캐시 정책·팩터 기본값은 변경하지 않는다.
- 갱신 실패 시 원천 검증의 안전한 한국어 사유와 조회 월, 검증 완료 페이지를
  표시한다. 일반 예외의 내부 상세는 노출하지 않으며, 실패 후 접수 안내는 숨긴다.

## 최신 수불 판매수량 원천 적용 — 온라인 포함 (2026-09-07)

### 갱신 연결 시간 초과 보완 (같은 날)

- 기존 수동 갱신은 HTTP 요청 하나가 24개월 조회와 전 법인 잠금을 기다렸다.
  로컬 Next 프록시의 기본 30초 제한으로 연결이 끊겨도 서버 작업은 계속될 수
  있어 화면의 `Internal Server Error`만으로 계산 실패를 판정할 수 없었다.
- `POST /order-logic-v3/season-factors/refresh`는 이제 **202 + 작업 상태**를
  즉시 반환한다. artifact 본문을 반환하던 이전 동기 응답 계약은 대체한다.
- `GET /order-logic-v3/season-factors/refresh/status`로 현재 권한 법인의
  대기·실행·완료·실패와 월/페이지 진행을 조회한다. HTTP 실제 경로에는 `/api`가
  앞에 붙는다. 수동 시작은 관리자만 가능하고 상태 응답에는 원장 행이 없다.
- 월간 자동 갱신과 수동 갱신은 같은 법인의 미완료 작업을 공유한다.
  단일 작업자가 법인별로 순차 처리하며, 대기 중인 화면에는 처리 중인 법인을
  표시한다. 완료·검증 실패·예외는 각각 결과 상태로 기록한다.
- 화면은 5초 간격으로 상태를 확인하고, 이동 후 돌아와도 진행 상태를 다시
  연결한다. 법인이 바뀌면 이전 법인의 비동기 응답을 버린다. 실패나 연결 지연을
  자동으로 새 계산 요청으로 바꾸지 않는다.
- 최초 수불 정책 전환을 위한 자동 작업은 완료된 새 정책 월별 캐시를 재사용한다.
  이후 정기 갱신과 새로운 수동 갱신은 기존 강제 재조회 정책을 유지한다.
- 이전 원천 active artifact는 화면에서도 `판매 기준 갱신 필요`로 표시한다.
  계산식·판매 인정 기준·계절지수 검증/적용 조건은 변경하지 않는다.
- 작업 상태는 프로세스 메모리에 있으며 재시작을 넘겨 보존되지 않는다.
  완료 artifact와 월별 캐시는 기존 영속 저장소에 남는다. 자동 갱신이 설정된
  환경에서는 미완료 대상이 다시 접수된다.

사용자가 새 수불 API 명세와 함께 온라인 판매 포함 및 적용을 승인했다.
V3 웹 수요와 월간 계절지수의 판매수량은 모두
`GET /api/v1/esm/stock-in-out`에서 **`OUT-SALE` + `OUT-SALE (ONLINE)`의
`qty_out` 합계**로 전환한다. 과거 아래 기록의 금액 양수·판매내역 거래유형
필터를 새 수불 수량에 적용하지 않는다. 반품·이동·재고조정은 제외하며
반품 차감으로 바꾸지 않는다. 단가·매출액을 가상 생성하지 않는다.

- HQ: `CO000001` + 오포 `WH000028`, PL: `CO000016` 전 창고,
  USA: `CO000007` 전 창고, 사업군 `COSMETIC`.
- 월간 자료는 직전 완료월까지 rolling **24개 완료 달력월**이며 이전 12개월과
  최근 12개월의 **1:2 가중**, 기능구분별 집계, 축소보정, SKU 수 `n`,
  기본값 1.0 적용 조건 등 기존 승인 산식은 유지한다.
- 상품분류는 판매상품 부분 목록이 아닌 전체 마스터를 조회한다. 상품코드
  정확 일치·상품명 완전 일치 시 대소문자 별칭·`.0` 보존 계약을 유지한다.
- 거래번호 `origin_no` 또는 같은 내용의 행으로 중복 삭제하지 않는다.
  예: 일반판매 32, 온라인 3, 재고조정 100이면 월 판매량 기여는 **35**다.
- 월별 모든 페이지를 검증한 후 일별 수량 집계를 캐시한다. 24개월 원장을
  한 번에 요청하지 않으며 웹의 91일 수요와 같은 월 집계 캐시를 공유한다.
  원장 거래번호·거래처·비고를 artifact에 기록하지 않는다.
- 계산 버전 `v3.8-stock-in-out-sale-online`,
  `source_request.demand_policy=V3_STOCK_IN_OUT_SALE_AND_ONLINE_V1`.
  포함 구분, 조회 범위, 집계 checksum 및 상품 연결 정책을 기록한다.
- 운영 전환 시 세 법인 각각 새 원천으로 계절지수를 다시 계산해야 한다.
  기존 팩터는 이름·기본값 정책만 바꿔 새 원천으로 표시할 수 없다.
  웹은 새 원천 정책이 아닌 active 팩터를 `SEASON_FACTOR_SOURCE_MISMATCH`로
  차단한다. 월간 스케줄러도 같은 완료월의 원천 정책 변경을 감지한다.
- CORE/GENERAL 등급의 **매출액** 산정은 기존 판매 API를 유지한다. 이는
  수불 **판매수량**으로 계산하는 계절지수와 별개의 입력이다.

세부 API 조회·캐시·전환 절차는
[`ORDER_LOGIC_V3_DISCOVERY_HANDOFF.md`](ORDER_LOGIC_V3_DISCOVERY_HANDOFF.md)의
2026-09-07 절을 따른다.

## 최신 해설서 V2 주간 적용단위 정정 (2026-09-01)

사용자는 첨부 해설서 V2를 V3 계산의 최신 기준으로 적용했다. 이 절은 아래의
`1기=28일`, 364일 관측창, 84일 무판매 보류 기록과 충돌할 때 우선한다.

- 계절지수 artifact 생성은 기존처럼 직전 완료월 기준 rolling 24개 완료 달력월과
  이전 12개월:최근 12개월=`1:2` 가중을 사용한다.
- SKU별 과거 수요 적용은 원천 일별 판매를 해당 날짜의 월 지수로 나눈 후
  **월요일~일요일 7일 × 완료 13주(91일)** 로 집계한다. 월 경계 주는 날짜별
  제거 결과를 합산하며 대표월 지수 하나로 대체하지 않는다.
- 미래 적용은 실측 리드타임과 28일 검토주기의 실제 달력일 구간에 월 지수를
  가중해 `f1`, `f2`, `fLR`을 구한다. 리드타임을 정수 주로 반올림하지 않는다.
- 기존 84일 무판매 보류는 제거됐다. 계절지수 연결과 별개로 전체 13주 이력 또는
  선택 엔진의 최소 유효 이력이 부족하면 일반 계산 차단으로 처리한다.
- `CV²>0.49` σ 강화 배수는 해설서에 산식이 없어 계절지수 명세에서도 추정하지 않는다.
  월 지수와 엔진 σ는 현재 승인된 계산대로 유지하고 `high_cv2`만 감사정보로 남긴다.

## 최신 PL 웹 분석 마스터 조회 범위 정정 (2026-08-31)

V3 웹 분석은 PL도 `eu_sold_only=false`로 전체 상품마스터를 조회한다. 판매상품
부분 목록에서 빠진 재고·미입고 대상의 기능구분을 현재 전체 마스터로 연결하기 위한
정정이다. 마스터만 있는 상품은 분석 모집단에 추가하지 않으며 상품명 완전 일치를
전제로 한 대소문자 코드 연결·`.0` 보존 정책은 그대로 유지한다.

이는 웹 입력의 분류 연결만 정정한다. 월간 팩터 생성의 조회·판매 모집단·축소보정
`n`·산식·기존 active artifact는 변경하지 않는다. 다른 법인의 팩터나 1.0을 새로
대입하지 않으며, 실제 미분류·팩터 부재·84일 무판매 보류 규칙을 유지한다.

## 최신 동일 제품 코드 연결·`.0` 보존 승인 (2026-08-31)

사용자 재확인: **상품코드가 대소문자만 다르고, 상품명도 공백·기호·괄호·용량
표기까지 완전히 일치할 때만 같은 제품으로 인식한다.** 상품명 조건을 제거했던
에이전트의 구현·기록은 요청 해석 오류로 정정하며, `.0` 보존 수정은 유지한다. V3 전용 원천
연결 모듈 `order_logic_v3_product_identity.py`를 웹과 월간 팩터 생성에서 공유한다.

- 상품명 원문과 대소문자만 다른 코드가 모두 일치하는 유일한 마스터 표기로 연결한 뒤 정상 유상 판매 필터·월 집계를
  실행한다. 같은 제품의 판매행은 합산하며 새 거래 중복 삭제는 하지 않는다.
  축소보정 SKU 수 `n`도 연결된 대표 코드 기준이다. 지수 산식·가중·기본값은 유지한다.
- 상품명을 trim·공백 축약·기호 제거·용량 환산·대소문자/Unicode 정규화하지 않는다.
  이름 불일치·충돌·근거 없음 또는 마스터 후보 중복이면 연결하지 않는다. 같은 원천코드의
  다른 행에서 이름 정확 일치가 확인되고 모순이 없을 때만 이름 없는 행도 검증된 연결을 따른다.
  마스터가 없으면 코드를 임의 변경하지 않는다. 원래 코드의 정확 일치는 기존 계약을 유지한다.
  `.0`은 모든 V3 판매·마스터 연결에서 보존한다. `Test2.0`과 `TEST2.0`은 상품명까지
  같을 때만 연결한다. `TEST2`는 별도 제품이며 숫자형 문자열의 `.0`도 임의로 지우지 않는다.
- 웹의 판매·재고·운송·미입고도 같은 연결을 적용한다. 기존 발주분석·V2·공통
  상품코드 정규화의 기본 동작과 CMS 원본·캐시는 변경하지 않는다. V3만 보존 옵션을 쓴다.
- 새 팩터 로직 버전은 `v3.7-exact-name-literal-code`다. artifact 원천 메타데이터에는
  `V3_CASE_INSENSITIVE_CODE_EXACT_PRODUCT_NAME_PRESERVE_SUFFIX_V3` 정책과 연결·거절 건수만
  기록한다. 원본 상품코드 목록·상품명·판매행은 artifact에 넣지 않는다.
- 기존 active 팩터를 웹 요청에서 다시 계산하거나 소급 변경하지 않는다. 다음
  명시적/정기 갱신부터 보정된 연결로 candidate를 생성하고 기존 기술 검증·활성화
  절차를 따른다. 팩터 미매핑·분류 누락에 새 기본값을 적용하는 승인이 아니다.

## 최신 SKU 분류·지수 연결 정정 (2026-08-31)

개별 SKU에 정상 유상 판매이력이 없어도 현재 상품마스터의 기능구분으로 동일 법인의
활성 계절지수를 연결한다. 기능구분1·2가 있으면 조합 지수, 기능구분2만 없으면
SF-015의 기능구분1 지수를 사용한다. 판매이력 없음 자체는 분류 누락이 아니다.
이는 웹 발주 입력 연결의 정정이며 월간 팩터 계산의 판매 모집단·축소보정 n·수치는
변경하지 않는다. 마스터만 있는 SKU를 발주 모집단에 추가하지도 않는다.

지수의 **연결 가능 여부**와 발주 계산의 **실제 적용·완료 여부**를 API·상세 화면·
Excel에서 구분한다. 지수가 연결돼도 기존 84일 무판매 보류 및 이력 부족 규칙은
유지한다. 실제 미매핑·프로파일 부재·artifact 오류를 1.0이나 타 법인 값으로 대체하지 않는다.

## 최신 화면 표시 결정 (2026-08-31)

사용자 요청에 따라 `보류·차단 사유` 패널의 한국어 안내 아래에는
`SEASON_FACTOR_MAPPING_MISSING` 등 내부 오류코드를 표시하지 않는다.
한국어 사유와 계산 차단 동작은 유지하며, API·Excel의 사유 코드도 변경하지 않는다.
이 결정은 아래의 해당 패널 reason code 표시 계약보다 우선한다.

계절지수 관리 화면에서 `DEFAULT_1` 상태에 표시하는 노란 안내에는 원래 실패
메시지와 내부 사유 코드도 표시하지 않고, 기본값 1.0 적용 안내만 표시한다.
원래 실패 사유는 artifact·API·Excel에 계속 보존한다.

## 최신 결정 — SF-018 (2026-08-31)

사용자는 계절지수 관리의 **계산 보류 항목을 모두 월별 기본값 1.0으로 적용**하도록
승인했다. 유효 artifact의 분류별 `SEASON_FACTOR_CALC_FAILED` 항목은 1~12월을
각각 1.0으로 저장하고 V3 계산을 계속한다. 정상 계산된 프로파일은 변경하지 않는다.
이 결정은 아래의 계산 실패 시 차단·1.0 대체 금지 규칙보다 우선한다.

기존 미산출 배경: 월별 계절지수 계산 중 0 이하인 값이 하나라도 있으면
`zero monthly factor`로 해당 분류의 프로파일 계산을 실패 처리했다. 과거 판매를
월별 지수로 나누는 계절성 제거 과정에서 0으로 나눌 수 없으므로, 기존 정책은
이 프로파일에 연결된 SKU의 발주 계산을 차단했다. 이는 해당 SKU의 판매가 전혀
없다는 뜻은 아니다. 예를 들어 두 해 모두 1월 집계 판매가 0이면 후보 1월 지수가
0이 될 수 있다. 실제 무판매인지 원천 누락 등인지는 별도 확인이 필요하다.
SF-018의 1.0 대체는 이 계산 차단을 해제하는 운영 정책이며, 원천 데이터의
정확성이나 수요예측 정확도, 계절성이 없다는 사실을 검증한 결과가 아니다.

- 과거 판매 100개는 `100÷1=100`, 미래 기초예측 120개는 `120×1=120`으로,
  계절성에 의한 가감 없이 처리한다. 기존 수요예측·재고·발주 산식은 유지한다.
- `DEFAULT_1` 상태와 `SEASON_FACTOR_CALC_FAILED_USE_DEFAULT_1` 적용 사유,
  원래 실패 코드·메시지, 적용 버전을 artifact·API·화면·Excel에 남긴다.
  이를 계절성 검증 성공 또는 계절성 미확인 판정으로 표시하지 않는다.
- 기존 active의 보류 항목도 새 버전으로 전환하고 직전 버전은 retired로 보존한다.
  월간 갱신에서도 같은 정책을 적용한다. 원천 판매를 재수집하지 않는 기존 버전
  전환에서는 원래 관측기간·계산시각을 보존하고 새 활성화 시각을 기록한다.
- 적용 범위는 HQ·PL·USA의 **계산된 artifact 내 분류별 계산 실패**다.
  artifact 자체 부재·검증 실패·stale, 분류 미매핑·프로파일 누락, 판매이력 부족,
  최근 84일 무판매 등 다른 차단·보류 사유는 자동 해제하지 않는다.

- 프런트엔드는 팩터를 계산하거나 운영 상수의 원본이 되지 않는다.
- 파일 저장 위치도 회사 데이터 저장에 해당할 수 있으므로 보안팀 확인이 필요하다.
- 보안 승인 후 DB나 사내 Object Storage로 옮겨도 계산 서비스의 조회 계약은 유지한다.

### 1.4 현재 구현 상태

- 현재 V3 화면은 fixture 기반 UI 검토 단계다.
- V3 시즌팩터 백엔드 loader, JSON artifact 저장소, 검증 후 자동 활성화와 이전
  `active`의 `retired` 보존 경로가 구현됐다. DB가 있으면 runtime snapshot,
  없으면 storage의 원자적 JSON 파일을 사용한다.
- 월간 스케줄러는 구현됐지만 공식 월 마감일이 미확정이므로 기본 비활성이다.
  실행일·시각 환경설정을 명시한 경우에만 월 1회 법인별 후보를 생성한다.
- `core/order_logic_v3.py`에는 24개 완료월의 교과서 월지수, 축소보정, 명시적
  계절성 미확인 1.0, 일자별 계절 제거, `f1`·`f2`·`fLR` 계산이 순수 함수로 있다.
- 동일 승인 팩터 버전으로 과거 계절 제거와 미래 재적용을 수행하고 쇼티지·
  현금흐름 두 시나리오를 같은 snapshot에서 반환하는 SKU 단위 진입점이 있다.
- API 결과 계약에는 SKU별 시즌팩터 버전·기능구분 코드·`f1`·`f2`·`fLR`와
  원본/계절제거 13기간이 포함된다. 팩터 법인 불일치·계산 실패는 해당 SKU의
  reason code로 직렬화한다.
- 기존 검증 메모의 고정 `2024:2025` 가중은 사용하지 않는다. 사용자 결정에 따라
  직전 완료월 기준 rolling 24개월의 이전 12개월:최근 12개월=`1:2` 가중으로
  일반화한다.
- 이 문서의 핵심 결정 게이트를 닫기 전 실제 발주수량에 시즌팩터를 적용하지 않는다.

### 1.5 새 설명자료에서 일치한 계산 흐름

두 DOCX와 Claude 테스트베드는 다음 순서를 공통으로 설명하며, 사용자가
**V3 백테스트 계산계약으로 확정**했다.

```text
과거 실적 ÷ 과거기간 시즌팩터
  -> 계절을 제거한 판매력으로 ADI·CV²·추세 판정
  -> SES / HOLT+감쇠 / Croston+SBA로 기초 d̄·σ 계산
  -> 미래 리드타임·검토기간 시즌팩터를 한 번 재적용
  -> Layer 1·2·3 -> 목표재고 S -> 순수 정기발주 Q=max(0,S-IP)
```

손검산 예시는 다음과 같다. 예시 수치는 운영값이 아니다.

```text
과거 6월 실적 2,100, 6월 팩터 2.0
계절 제거 판매량 = 2,100 ÷ 2.0 = 1,050

기초 d̄ = 1,073.84, 미래 4월 팩터 = 0.7
Layer 1용 재계절화 d̄ = 1,073.84 × 0.7 = 751.688 ≈ 751.7

기초 d̄ = 1,073.84, 미래 5월 팩터 = 1.1
Layer 3용 재계절화 d̄ = 1,073.84 × 1.1 = 1,181.224 ≈ 1,181.2
```

이는 “기초예측에 원실적을 넣고 미래 팩터만 추가 곱”하는 구조와 다르다.
계절 제거 없이 분류하면 계산 엔진 자체가 달라질 수 있으므로, 두 구조를 혼용하지
않는다.

## 3. 기존 검증 메모와 이번 회의 방향의 충돌

기존 검증 메모는 다음 후보 규칙으로 계산했다.

- 연결 가능한 HQ·PL·USA 판매이력과 현재 상품 마스터를 사용
- `class1` 단위로 월별 판매수량을 집계
- 연도별 월평균을 1.00으로 정규화
- 2024년과 2025년 프로파일을 1:2로 가중
- 두 연도 상관과 진폭 기준으로 적용 여부 판단
- 실물 카테고리에서는 선케어만 검증 기준을 통과했다는 결론

이번 회의 방향은 `기능구분1 × 기능구분2 × 기간`의 rolling 2년 팩터표다.
따라서 아래 항목은 같은 것으로 간주하면 안 된다.

| 구분 | 기존 검증 후보 | 이번 회의 방향 | 상태 |
| --- | --- | --- | --- |
| 분류 grain | `class1` | 기능구분1 × 기능구분2 | 미결 |
| 적용 범위 | 검증 통과한 실물 카테고리 | 전체 또는 일부 기능구분 조합 | 미결 |
| 기간 | 고정 2024~2025 예시 | 매월 rolling 24개월 | 회의 방향 |
| 연도 가중 | 2024:2025 = 1:2 | 직전 완료월 기준 이전 12개월:최근 12개월 = 1:2 | **SF-005 확정** |

### 4.2 팩터 적용 기간

| 선택 | 의미 | 장점 | 위험 |
| --- | --- | --- | --- |
| 주문월 팩터 | 분석 실행일이 속한 월 값 사용 | 단순함 | 리드타임 뒤 판매 시기와 어긋남 |
| 예상 도착월 팩터 | 발주품이 도착하는 월 값 사용 | 실제 보충 시점과 가까움 | 여러 운송수단·ETA 처리 필요 |
| 보호기간 일수 가중 | 리드타임·다음 검토기간에 걸친 월별 팩터를 일수로 가중 | 발주식 기간과 가장 잘 맞음 | 구현·설명·검산이 복잡함 |

**사용자 결정(2026-08-27): C. 리드타임 구간과 다음 검토 구간에 포함되는
월별 팩터를 일수로 가중한다.**

개념식은 다음과 같다.

```text
f1 = Σ(리드타임 구간에 포함된 월별 일수 × 해당 월 팩터)
     ÷ 리드타임 구간 전체 일수

f2 = Σ(다음 검토 구간에 포함된 월별 일수 × 해당 월 팩터)
     ÷ 다음 검토 구간 전체 일수
```

손검산용 예시이며 운영값은 아니다.

```text
리드타임 구간: [2026-10-01, 2026-12-01) = 61일
10월 팩터 0.8, 11월 팩터 1.0
f1 = (31일 × 0.8 + 30일 × 1.0) ÷ 61일
   = 54.8 ÷ 61
   ≈ 0.8984

다음 검토 구간: [2026-12-01, 2026-12-29) = 28일
12월 팩터 1.4
f2 = (28일 × 1.4) ÷ 28일 = 1.4
```

백테스트의 일자 구간은 위 손검산과 같이 `[시작일, 종료일)`로 계산하고 중간값은
반올림하지 않는다. CMS `출고일`은 이미 확정된 원천 달력일이므로 법인·창고
시간대·UTC·DST 변환을 하지 않는다. 화면 표시 반올림은 운영 계약에서 추가
확정한다.

**사용자 결정(2026-08-28):** 실측 리드타임과 검토주기는 소수 일수를 포함할 수
있다. 따라서 `f1`, `f2`, `fLR`의 `[시작일, 종료일)` 경계는 소수일을 보존하며,
리드타임을 정수일 또는 28일 기 단위로 반올림하지 않는다. 월 팩터는 해당 월에
속한 소수 시간만큼 가중한다.

### 4.6 Layer 2 안전재고의 시즌팩터

교과서의 L=R=한 기간 예시는 4월 0.7과 5월 1.1의 단순 평균 0.9를 만들어
Layer 2용 d̄와 σ에 모두 곱한다. 실제 운영에서는 L과 R의 길이가 다르고 여러
달에 걸칠 수 있으므로 단순 `(f1+f2)/2`는 사용할 수 없다.

| 선택 | 규칙 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. `fLR` 일수 가중 | `L+R` 전체 실제 날짜에 대해 월 팩터를 달력일 수로 가중하고 기초 d̄·σ에 동일 곱 | 교과서의 0.9 예시를 불균등 기간에도 일관되게 일반화 | σ가 팩터에 선형 비례한다는 가정 필요 |
| B. 평균·분산 별도 적분 | 기간별 예상수요와 오차분산을 월별로 따로 합산 | 통계적으로 가장 명시적 | 원천 오차모형과 구현 복잡도 증가 |
| C. 평균수요만 보정 | d̄에는 `fLR`, σ에는 기초값 유지 | 보수적이고 단순 | 교과서 예시와 달라지고 성수기 오차변동을 반영 못함 |

**사용자 결정(2026-08-27): A안 확정.** `L+R` 실제 날짜에 포함된 월 팩터를
달력일 수로 가중한 `fLR`를 기초 d̄와 σ에 동일하게 곱한다. 단순
`(f1+f2)/2`는 L과 R의 길이가 같고 같은 날짜구성을 가질 때만 같은 값이 된다.

### 4.7 과거 4주 실적의 월 팩터 매핑

테스트베드는 13기 시작월이 3월이면 다음 미래기간을 4월·5월로 표시한다.
그러나 1기간이 정확히 4주라면 달력월과 길이가 같지 않다. 검토한 방식은 다음과
같으며 운영 규칙은 A안으로 확정했다.

| 선택 | 규칙 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. 원천 일자에서 먼저 제거 | 판매일별로 해당 달 팩터를 나눈 뒤 4주 기간으로 집계 | 월 경계가 정확하고 권고안과 정합 | 원천행 처리량 증가 |
| B. 4주 구간 팩터를 일수 가중 | 4주 구간의 월별 겹친 일수로 팩터를 만든 뒤 집계 판매량을 나눔 | 월간 사전집계에도 적용 가능 | 일별 판매 분포가 균등하다고 가정 |
| C. 시작월 또는 대표월 하나 사용 | 한 달의 팩터만 적용 | 단순 | 월 경계와 13기간 누적 드리프트 오류 |

**사용자 결정(2026-08-27): A안 확정.** 판매일별로 해당 달 팩터를 먼저 나눈 뒤
완료된 4주 기간으로 합산한다. 월간·4주 집계만 있어 일자별 제거가 불가능한 원천은
B안으로 자동 대체하지 않고 계산을 차단한다. C안은 운영에서 사용하지 않는다.

## 6. 버전형 팩터 파일의 최소 메타데이터

파일 형식은 아직 확정하지 않지만 다음 의미를 잃으면 안 된다.

```text
version
status: candidate | active | retired
window_start
window_end
calculated_at
validated_at
activated_at
calculation_logic_version
source_scope
classification_version
checksum
factors[]:
  entity_or_market
  function_class_1_code
  function_class_2_code
  calendar_month
  factor
  application_status
  reason_code
```

- 팩터 파일에 원본 판매행을 포함하지 않는다.
- 실제 판매량·매출액·표본수를 파일에 넣을지는 보안 검토 후 결정한다.
- 프런트는 이 파일을 직접 읽지 않는다.
- 백엔드는 스키마·중복키·월 1~12 완전성·checksum을 확인한 뒤 활성화한다.

## 7. 월간 운영 절차

```text
1. 설정된 원천 마감 시점 도달 확인
2. rolling 24개월 조회
3. 정제·분류 연결
4. candidate 팩터 계산·버전 저장
5. 스키마·기간·중복키·1~12월 완전성·checksum 기술 검증
6. 검증 통과 시 같은 작업에서 active 자동 전환
7. 직전 active를 retired 버전으로 보존
8. V3의 새 active 조회 확인
9. 대표 SKU 손계산 대조
10. 문제 시 직전 retired 버전 롤백
```

배치 실패 시 실패한 후보를 활성화하거나 기존 버전을 최신으로 위장하지 않는다.
화면에 `갱신 지연`과 실제 적용 버전을 표시한다. 기존 `active`의 유효기간 안에서는
그 버전을 사용할 수 있으나, 정확한 유효기간은 `SF-008`에서 확정한다. 유효
`active`가 없거나 `stale`이면 해당 SKU 계산을 차단하고 사유를 표시한다.

**인터뷰 확인(2026-08-27):** 사용자는 HQ·PL·USA의 전월 판매 데이터가 매월
몇 영업일에 확정되는지 알지 못하며, 저장소에서도 공식 월 마감일을 확인하지 못했다.
따라서 `매월 5일` 같은 실행일이나 마감 대기일을 추정해 하드코딩하지 않는다.
원천 데이터 담당자의 마감 확인 방법과 책임자를 확인하기 전까지 `SF-008`은
외부확인 필요 상태로 유지했다. 이후 사용자 결정으로 월간 실행은 **매월 1일
03:00 KST**로 확정했으며, 구현된 스케줄러의 환경설정에도 반영한다.

교육용 테스트베드처럼 월별 팩터를 자유롭게 편집하는 기능은 운영 기본 UI에 넣지

권한, 사유, 변경 전후 값, 승인자, 만료일, 롤백을 포함하는 별도 정책을 먼저 승인받는다.

## 10. 구현 금지·프로젝트 규칙

1. 이 문서의 **미결** 항목을 개발자가 편의상 기본값으로 정하지 않는다.
2. 시즌팩터 산식 또는 발주수량 영향을 바꾸기 전에 자연어 계산 계획과 손검산
   예시를 사용자에게 제시하고 승인을 받는다.
3. 월간 사전계산과 웹 요청 계산의 경계를 유지한다.
4. 프런트에서 운영 팩터를 계산하거나 하드코딩하지 않는다.
5. 운영 팩터의 단일 원천은 승인된 백엔드 artifact다.
6. `팩터 1.0`, 상위분류, 직전버전 사용을 암묵적 fallback으로 넣지 않는다.
7. 실행 결과와 Excel에 팩터 버전·관측기간·적용값을 추적 가능하게 남긴다.
8. 원본 CMS 행, 인증정보, 실제 민감 데이터를 저장소나 문서에 기록하지 않는다.
9. DB가 존재한다고 가정하지 않는다. 파일 저장도 보안 승인 범위에 포함한다.
10. 기존 발주분석·V2·V3의 코드와 계산 결과 경계를 유지한다.
11. 인터뷰 답변을 아래 결정 로그에 날짜와 함께 기록한 뒤 구현한다.
12. 결과 검증에는 대표 SKU 손계산, 화면/API/Excel 대사, 회귀 테스트를 포함한다.
13. 교과서·테스트베드의 예시값이나 브라우저에서 수정 가능한 값을 운영 기본값으로
    복사하지 않는다.
14. `계절성 검증 결과 1.0`, `저표본 보정 1.0`, `누락 fallback 1.0`을 같은 상태로
    저장하거나 표시하지 않는다.
15. 4주 기간을 시작월·종료월 하나로 단순 치환하지 않는다. SF-013 확정 규칙에 따라
    실제 날짜 경계를 사용한다.

## 12. 인터뷰 진행 원칙

- 한 번에 모든 질문을 묻지 않고, 숫자 의미를 크게 바꾸는 질문부터 하나씩 묻는다.
- 각 질문에는 선택지, 장단점, 추천안을 함께 제시한다.
- 사용자가 답하면 이 문서의 결정 로그와 관련 계약 항목을 즉시 갱신한다.
- 답변이 애매하면 구현값으로 해석하지 않고 후속 질문으로 확인한다.
- 계산식 질문에는 손으로 확인 가능한 예시 숫자를 함께 사용한다.

## 13. 첫 구현 전 종료 조건

최소한 `SF-001`~`SF-009`와 계절 적용 순서를 다루는 `SF-011`~`SF-013`이
확정되고 다음 자료가 있어야 한다. `SF-010`은 파일럿 실행 전까지 확정한다.

- 승인된 팩터 계산 계약
- 분류키·원천필드·중복제거 계약
- 월간 운영·자동 활성화·롤백 절차
- 보안 승인된 artifact 저장 위치
- 누락 시 차단 정책과 stale 판정 시점·배치실패 시 기존 active 유효기간
- 대표 카테고리와 SKU의 기대값 fixture
- 과거 계절 제거·Layer 1/2/3 재적용을 모두 포함한 기대값 fixture
- 화면/API/Excel 추적성 계약

위 조건을 충족하기 전에는 실제 발주수량에 시즌팩터를 연결하지 않는다.
