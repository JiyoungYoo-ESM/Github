## 최신 PL 두 시나리오 철송 전환 승인 — 2026-09-08

사용자 요청(`오늘 날짜 기준으로 pl만 cash, shortage 둘 다 철송을 기준으로
로직 적용해줘`)으로 PL(EU)의 V3 시나리오별 운송수단을 변경한다.
이 절은 V3-009 결정표의 PL 행(`CASH=RAIL, SHORTAGE=SEA`)을 대체한다.

- **PL은 CASH·SHORTAGE 두 시나리오 모두 `RAIL`(철송)** 실측 리드타임을
  사용한다. 두 시나리오의 `L`·`sigma_L`이 같아지고 Z만 다르다(HQ와 동일한

- 직전 6개월 완료 Packing No 실측, 모드별 최소 10건 차단, `/28` 기 단위

- **SEA 실측은 계속 수집한다.** PL의 운송중 ETA 추정은 Invoice 비고에서
  판정한 실제 운송수단을 따르므로, 해운 운송중 건에는 여전히 SEA 실측 평균
  LT가 필요하다. `_v2_eta_config`가 시나리오 감사정보에 없는 모드를
  `lead_time_audit.source.modes`의 실측 평균에서 보충하도록 확장했다.
  따라서 PL의 SEA 표본이 10건 미만이면 종전과 같이 계산이 차단된다.
- 구현: `backend/services/order_logic_v3_source.py`의 `_V2_SCENARIO_MODES`
  PL 행과 실측 대상 모드 분리(`_V3_MEASURED_LEAD_TIME_MODES`),
  `backend/services/order_logic_v3_shipping.py`의 ETA 평균 보충.
  로직 버전 `v3.32-pl-rail-both-scenarios`, 결과 schema `25` 유지.
  과거 완료 결과는 소급 변경하지 않으며 재분석부터 적용된다.
- 검증: V3·리드타임 백엔드 테스트 547개 통과(변경 반영 갱신 포함).

## 최신 박스 올림 최종 주문수량 승인 — 2026-09-08

### USA 인박스는 `inbox_cnt_usa`만 사용 — 2026-09-08 추가 결정

CMS팀이 `/eu/products`가 이름과 달리 **전사 공통 상품마스터(TB_PROD) 전체**를
반환하며 `inbox_cnt`/`outbox_cnt`도 전사 공통값임을 확인해 주었다. 이어
`inbox_cnt_usa`(미주 전용 인박스)·`inbox_cnt_inner`·`moq`(전사 공통)·`moq_usa`
4개 필드를 추가 배포했다. 실측으로 공통값과 미주값이 양방향으로 다르다
(ECM96-Cr 1→6, ECM96-ISch 10→6, SNC08-GP 50→5). 채움률: `inbox_cnt_usa`
8.1%, `inbox_cnt_inner` 4.5%, `moq` 3.1%, `moq_usa` 1.7%.

**사용자 결정(2026-09-08): "미주 값이 없으면 그냥 없는 셈 친다(지금처럼
10단위 올림). 미주 별도로 있는 값은 미주 발주 V3에서만 적용."**

- USA 올림 사다리: 아웃박스(`outbox_cnt`) → **`inbox_cnt_usa`** → 10단위.
  `inbox_cnt_usa`가 없으면 전사 공통 `inbox_cnt`로 대체하지 않고 바로
  10단위 fallback으로 간다. 실물 박스가 양방향으로 다르므로 공통값 대체는
  과대·과소 발주를 모두 만들 수 있다.
- HQ·PL 사다리는 기존 그대로 `outbox_cnt` → `inbox_cnt` → 10단위.
  `outbox_cnt`는 지역 변형이 없어 세 법인 공통이다.
- `inbox_cnt_inner`·`moq`·`moq_usa`는 이번 결정에 포함되지 않았다. MOQ는
  V3-012 잔여 제약으로 별도 승인 전 적용하지 않는다.
- 구현: `_product_pack_quantities(entity_code=...)`가 USA일 때만
  `inbox_cnt_usa`를 읽는다. 결과의 `order_unit_policy.inbox_source_field`
  감사값으로 어느 필드를 썼는지 남긴다. 로직 버전
  `v3.33-usa-inbox-cnt-usa-pack`, schema는 행 구조 불변으로 기존 유지.
- 상품마스터 캐시에 새 필드가 없을 수 있어 USA 첫 적용 시 `force_refresh`
  재분석이 필요하다.

CMS팀(이재훈 과장)이 `GET /api/v1/eu/products` 응답에 `inbox_cnt`(인박스
입수량)·`outbox_cnt`(아웃박스 입수량)를 추가 배포했다(미설정은 null 통일,
채움률 inbox 52.3%/outbox 33.6%, `inbox_cnt_usa` 등 지역 변형 컬럼은 미포함).
사용자는 아래 올림 사다리와 손검산, 그리고 3개 확정 답변(최종 주문수량으로
확정 / 발주금액은 올림 수량 기준 / 화면·Excel은 원시값과 나란히 표시)으로
승인했다. 이 절은 V3-012의 "박스 올림 미산출" 상태를 부분 해제한다.
MOQ·팔레트·최소주문금액 제약은 계속 미확정·미적용이다.

- **올림 사다리(HQ·PL·USA 공통):** `Q_raw > 0`인 SKU만
  `final = CEILING(Q_raw / 단위) × 단위`. 단위는 ① `outbox_cnt`가 유효하면
  아웃박스, ② 아니면 `inbox_cnt`, ③ 둘 다 없으면 **10**. null·0·음수·비숫자
  입수량은 모두 미설정으로 본다. `Q_raw = 0`은 0 유지(박스 1개를 만들지 않음).
- **손검산(승인):** `Q_raw=205.3`, outbox=160 → 320. outbox 없음, inbox=20 →
  220. 둘 다 없음 → 210. `Q_raw=0` → 0.
- **발주금액:** `order_amount_krw`·`order_amount_local` 모두
  `final_order_quantity × 단가`로 변경. 원시 수량 기준 금액은 저장하지 않는다.
- **결과 계약:** 행에 `final_order_quantity`, `order_unit_quantity`,
  `order_unit_source`(OUTBOX/INBOX/FALLBACK_10), `inbox_quantity`,
  `outbox_quantity`를 추가. `raw_order_quantity`는 그대로 보존.
  `order_constraint_status`는 `PACK_ROUNDING_APPLIED`로 전환하고 summary의
  `final_order_quantity`는 계산 가능 SKU 합계를 채운다. 차단 행은 계속 null.
- **화면·Excel:** 최종 주문수량을 메인으로, 원시 필요량과 주문단위를 나란히
  표시. 검토 기본수량(finalQty)도 최종 주문수량에서 시작한다. Excel 발주제안에
  `최종 주문수량(박스 올림)`·`주문단위` 열을 추가하고 `_계산기준`에 원천
  inbox/outbox와 단위 출처를 남긴다.
- **원천:** 세 법인 모두 기존 V3 상품마스터(`/eu/products` 전역 마스터)에서
  SKU별 pack 값을 읽는다(`_product_pack_quantities`, 정확 코드·`.0` 보존·
  마지막 행 우선의 기존 식별 정책과 동일). 상품마스터 캐시가 남아 있으면 새
  필드가 없을 수 있으므로 첫 적용 시 `force_refresh` 재분석이 필요하다.
- 구현: `core/order_logic_v3.py`의 `round_v3_order_quantity`(순수 함수),
  `backend/services/order_logic_v3_service.py`, `order_logic_v3_source.py`.
  로직 버전 `v3.30-pack-rounded-final-quantity`, 결과 schema `25`.
  과거 완료 결과는 소급 변경하지 않으며 재분석부터 적용된다.
- 검증: 백엔드 전체 1,235개 통과(신규 pack 올림·pack 매핑 테스트 포함),
  프런트 `tsc --noEmit`·V3 Excel·entity-scope·brand-search·export-transport·
  scenario-comparison·delivery·job-session 통과. `order-v3-review-list.test.mjs`는
  기존 `DEMAND_HORIZON_LABEL` 미정의로 계속 실패하며 이 작업과 무관하다.
  실제 CMS 재분석·화면 대조와 채움률 낮은 SKU(10단위 fallback 비중)의 운영
  확인은 사용자 확인이 필요하다.

## HOLT 초기화: 2점 차분 → 첫 6주 회귀 — 2026-09-08

사용자는 PL 실사례 3건(ALSC01-FbrEU·MNC10-OCDeep200·MNS02-T)의 과대 발주
원인 분석("초기추세오류 오답노트")을 검토한 뒤, 확정 산식 이미지를 첨부하며
**"식을 이렇게 적용하면 된대"**, "이걸로 로직을 바꿔줘"라고 승인했다.
HQ·PL·USA 공통이며 HOLT+감쇠 경로(TREND_UP/TREND_DOWN)에만 적용된다.

- **원인:** 기존 초기화 `FIRST_VALUE_FIRST_DIFFERENCE`는 `b0 = 2주차 − 1주차`
  로, α·β 평활을 거치지 않고 100% 그대로 재귀식의 출발값이 된다. 신상품
  초반 1회성 대량판매(스파이크)가 있으면 4단계 추세판정(앞6주 vs 뒤6주,
  올바르게 하락 판정)과 정반대인 급성장 초기추세로 출발해, 리드타임이 긴
  법인에서 L1·L2가 함께 폭증했다(MNC10: 13주 총판매 3,440 → Q_raw 22,589).
- **승인 산식(6주 기준, 정수 가중치 형태):**
  `b0 = (−5·Y1 − 3·Y2 − 1·Y3 + 1·Y4 + 3·Y5 + 5·Y6) ÷ 35`
  (t=1..6 최소제곱 회귀 기울기와 동치), `l0 = AVERAGE(Y1..Y6) + b0 × 2.5`
  (회귀선의 6주차 값). 재귀식은 7~13주차 관측치만 소화해 같은 주가 초기값과
  재귀에 이중 반영되지 않는다.
- **유지:** α=0.2·β=0.1·φ=0.9 재귀식, RMSE 산출, 4단계 추세판정(6 vs 6,
  7주차 제외), SES·Croston+SBA·이동평균 경로, 재계절화·Layer 1·2·3·
  `S`·`Q_raw` 산식은 전부 그대로다.
- **손검산(테스트 고정값):** 상승 fixture `280..480` → `b0=17.714286`,
  `l0=374.285714`, next=470.24. 스파이크 사례 MNC10 원판매
  `195, 1492, 954, 34, 10, 94, …` → 구식 `b0=+1,297/주`가 새식
  `b0=−167.74/주`로 방향까지 정정되고 RMSE 2,261→324로 줄어든다.
- 구현: `core/order_logic_v3.py`의 `calculate_holt_damped_forecast`와
  파라미터 게이트가 `SIX_WEEK_REGRESSION`만 허용한다. 로직 버전
  `v3.31-holt-six-week-regression-init`(같은 작업트리의 팩 라운딩 v3.30
  변경을 포함해 재분석부터 함께 적용된다). 행 구조는 바뀌지 않아 결과
  schema는 25를 유지한다. 과거 완료 결과는 소급 변경하지 않는다.
- 검증: 백엔드 전체 1,234개 통과(스파이크 회귀 테스트
  `test_holt_six_week_regression_init_is_not_poisoned_by_a_launch_spike`
  추가). 하락 SKU는 미래 주차 예측이 음수가 될 수 있으며 Layer 적분에서
  음수 기여로 반영된다 — 별도 0 클램프는 승인되지 않아 추가하지 않았다.
  실제 CMS 재분석·화면 대조는 사용자 확인이 필요하고, **백엔드 재시작
  후에만 새 로직이 적용된다.**

## 최신 판매 13주 미만 SKU 이동평균 적용 — 2026-09-08

사용자는 "판매 13주기 이하들은 이동평균으로 계산하는 로직"을 요청하고, 아래
판정 기준·산식·손검산을 승인한 뒤 **"진행해"**라고 확정했다. HQ·PL·USA 세 법인
공통이며 다른 SKU의 SES/HOLT+감쇠/Croston+SBA 경로는 변경하지 않는다.

- **판정 기준:** 13개 완료 주 창 안에서 최초 판매가 있는 주가 1주차보다 늦으면,
  즉 계절 제거된 13주 배열의 선행 주가 0으로 시작하면 창 내 판매이력이 13주
  미만인 SKU로 본다. 91일 웹 원천은 생애 최초 판매일을 증명할 수 없으므로
  판정은 창 내 증거로만 한다(기존 `first_sale_date` 감사 정책 유지).
- **산식:** 창 내 최초 판매주부터 마지막 완료주까지의 계절 제거된 주 판매
  단순평균을 `d_bar`로, 같은 구간의 표본표준편차 `STDEV.S`를 σ로 사용한다.
  중간 무판매 주는 0으로 포함한다. SES/HOLT/Croston 분류 게이트는 건너뛰며
  ADI·CV²는 감사값으로만 남긴다. 결과 행의 `pattern=SHORT_HISTORY`,
  `engine=MOVING_AVERAGE`이고 α·β·φ는 적용하지 않으므로 null이다.
- **유지:** Z 행렬·안전재고 fence·미래 계절 재적용(f1/f2/fLR)·리드타임·
  `S=L1+L2+L3`·`Q_raw=max(0,S-IP)`·IP 구성은 기존 그대로다. Layer 1·3은
  `d_bar×기간×팩터`, Layer 2 σ는 이동평균 σ에 fLR를 적용한다.
- **계속 차단:** 13주 전부 0 판매는 기존대로 차단한다. 창 내 판매주가 마지막
  1개뿐이어서 `STDEV.S`를 만들 수 없는 SKU는 σ를 0이나 임의값으로 채우지 않고
  `DEMAND_HISTORY_INSUFFICIENT`로 차단한다.
- **승인 손검산:** 첫 판매가 9주차, 계절 제거 주 판매 `10, 20, 30, 20, 20` →
  `d_bar = 100÷5 = 20`, `σ = STDEV.S ≈ 7.07`. 1주차부터 판매가 있는 SKU는
  뒤쪽 주가 0이어도 이동평균 대상이 아니다(기존 분류 유지).
- 구현: `core/order_logic_v3.py`의 `classify_v3_demand` 선행 게이트와
  `calculate_moving_average_forecast`. 로직 버전
  `v3.29-short-history-moving-average`, 결과 schema는 행 구조가 바뀌지 않아
  기존 `24`를 유지한다. 과거 완료 결과는 소급 변경하지 않으며 재분석부터
  적용된다.
- 검증: 백엔드 전체 1,228개 통과, 프런트 `tsc --noEmit`·V3 Excel·entity-scope·
  brand-search 회귀 통과. `order-v3-review-list.test.mjs`는 이 변경과 무관한
  기존 `DEMAND_HORIZON_LABEL` 미정의로 실패하며(변경 제거 후에도 동일 실패)
  이 작업에서 수정하지 않았다. 실제 CMS 재분석·화면 대조는 사용자 확인이
  필요하다. **백엔드 재시작은 사용자 결정(2026-09-08)에 따라 보류 중이며,
  진행 중인 USA 계절지수 갱신이 끝난 뒤 재시작해야 새 로직이 적용된다.**

## 최신 판매수량 원천 전환 — 수불 OUT-SALE·온라인 포함 (2026-09-07)

사용자는 새 `GET /api/v1/esm/stock-in-out` API 명세를 제공하고
**"온라인도 포함이래 그리고 위 기준으로 적용을 진행해줘"**라고 승인했다.
이 절은 아래 과거 기록의 **V3 판매수량에 대한 판매내역 금액·거래유형 필터**보다
우선한다. 예측·발주 산식과 기존 발주분석·V2는 변경하지 않는다.

- 판매수량: `ledger_type_nm`이 정확히 `OUT-SALE` 또는 `OUT-SALE (ONLINE)`인
  행의 `qty_out` 합계. 금액이 없는 원천이며 `amount > 0` 조건이나 가상 금액을
  넣지 않는다. 수량 0인 행은 기여하지 않는다.
- 재고조정·창고이동·입고·반품 등 나머지 수불구분은 판매수요에서 제외한다.
  반품을 판매량에서 차감하는 순판매 산식으로 바꾸지 않는다. 새로운 미확인
  구분을 이름의 접두어만 보고 판매로 포함하지 않는다.
- 손검산 예: 일반판매 32 + 온라인판매 3 + 재고조정 출고 100 → 판매량 **35**.
  `origin_no`가 같거나 행의 필드가 같다는 이유로 삭제하지 않는다. 실제 판매
  3개짜리 행 두 개는 **6**이다. 거래번호는 원장 행의 고유키가 아니다.
- 현재 가용재고는 기존 재고 API를 사용한다. 수불 `qty` 누적으로 현재 재고를
  만들지 않는다. 미입고·입고예정·운송중·단가·환율·리드타임 연결도 유지한다.
- CORE/GENERAL 상품등급은 기존 판매 API의 최근 완료 13주 **매출액**으로
  산출한다. 수불 API에는 금액이 없으므로 판매내역 API를 삭제하지 않는다.
  매출액이 연결되지 않은 상품의 기존 GENERAL 처리는 유지하고 감사 건수를 남긴다.

### 조회·검증·캐시

## 최신 V3 미입고 조회창 최근 30일 축소 — 2026-09-04

사용자는 V3에서 **발주가 필요해 보이는 SKU가 결과에 나타나지 않는 현상**을
보고했다. 화면 필터 문제가 아니라 계산 과정에서 제안수량 0(발주 불필요)으로
판정돼 사실상 사라지는 것이 원인으로 지목됐고, 그 원인으로 **미입고 수량 집계
범위**가 확인됐다. 이에 따라 **① 미입고 수량만** PO 등록일 기준 최근 30 달력일로
좁힌다. HQ·PL·USA 세 법인 모두에 동일하게 적용한다.

### 확인된 원인

기존 V3는 CMS 미입고현황을 `as_of` 연도의 **1월 1일부터 전부** 가져왔다. 이 값은
`backend/services/request_validation.py`의 `cms_date_settings()`가 만드는
`logistics_period_start`(= `as_of`의 1월 1일)이며, 운송중(shipping) 조회창과
공유하던 값을 미입고에도 그대로 쓴 결과였다.

그 결과 오래전에 등록됐지만 실제로는 유효하지 않거나 이미 처리됐어야 할 PO
잔량까지 계속 입고예정으로 잡혔다.

```text
오래된 미입고 잔량 누적 → 입고예정(①+②+③) 과대 → IP 과대
→ 발주필요수량 max(0, S − IP) 축소 → 일부 SKU가 제안수량 0으로 판정
```

즉 이전에 "왜 발주해야 할 SKU가 사라지는가"로 봤던 현상은 산식 오류가 아니라
**오래된 미입고 물량의 과대계상**으로 설명된다.

### 결정 — ① 미입고 수량만, 최근 30 달력일

- 기존: `2026-01-01` 이후 전체 미입고
- 변경: **PO 등록일 기준 최근 30 달력일**. `as_of`를 포함하며
  `date_from = as_of − 29일`, `date_to = as_of`다. 경계 두 날짜는 모두 포함한다.
- 기준 필드는 **PO 등록일**이며 입고일·ETA·선적일이 아니다. CMS
  `/eu/open-po`·`/us/open-po`의 `date_from`/`date_to`가 PO 등록일이라는 정의
  (`docs/cms_openapi.json`, `docs/CMS_API_GUIDE.md`)를 그대로 따른다.
- **적용 범위는 ① 미입고 수량 하나뿐이다.** 사용자 확인(2026-09-04):
  *"이미 입고 통보, 입고 진행중인 물량은 확실히 들어올 물량"* 이므로 **② PNFM확정·
  ③ 입고진행중·④ 입고완료는 PO 등록일이 오래되었다는 이유로 빼지 않는다.**
- SKU의 미입고/입고 원천 행 존재 여부(`inbound_status_source_present`),
  상품명·바코드 등 식별 증거, 계산 SKU 모집단도 창 적용 전과 같다. 창은 수량
  하나만 바꾸며 상품을 분석에서 사라지게 하지 않는다.
- **음수 미입고는 PO 등록일과 무관하게 계속 차단한다(사용자 결정 2026-09-04).**
  CMS는 `PNFM 수량 > PO 수량`인 행에서 음수 미입고를 반환하는데, V2가 이를
  `INCOMING_QTY_NEGATIVE`로 계산 차단하는 불량 데이터로 취급한다. 창을 좁힌
  결과로 음수가 0이 되면 그 fail-closed 검증이 조용히 사라지므로, 창 밖 음수는
  0으로 덮지 않고 원값을 그대로 내려보낸다. HQ·PL·USA 모두 동일하다.
- 상수·helper는 `backend/services/order_logic_v3_unreceived_window.py`의
  `V3_UNRECEIVED_LOOKBACK_DAYS = 30`과 `unreceived_po_window()` 한 곳뿐이다.
  법인별 적용 지점이 달라도 창의 정의는 하나이며, 감사값도 같은 helper에서
  나오므로 조회 범위와 기록이 어긋날 수 없다.

### 법인별 적용 지점 (HQ·PL·USA 전부 적용)

원천 API의 형태가 달라 적용 지점만 다르고, 창의 정의와 길이는 세 법인이 같다.

| 법인 | ① 미입고 원천 | 30일 창 적용 방식 | ②③④ |
| --- | --- | --- | --- |
| HQ | `GET /opo/po/open` | 창을 벗어난 행의 `remaining_qty`만 `0`으로. 행은 남기고, 음수는 0으로 덮지 않는다 | `/opo/inbound/confirmed` 별도 조회라 영향 없음 |
| PL | `GET /eu/open-po` | 같은 피드를 전체 창·30일 창으로 두 번 조회해 ① 계열 수량만 교체 | 전체 창 값 유지 |
| USA | `GET /us/open-po` | 같은 피드를 전체 창·30일 창으로 두 번 조회해 ① 계열 수량만 교체 | 전체 창 값 유지 |

- HQ는 행을 **삭제하지 않고 수량만 0으로** 만든다. 행을 지우면 원천 행 존재
  여부, 식별 증거, 그리고 판매·재고·확정입고가 없는 SKU의 경우 SKU 자체가
  모집단에서 사라진다. 이번 변경의 목적은 그 반대다.
- PL·USA 응답은 상품 단위 집계라 행에 PO 등록일이 없어 로컬 필터가 불가능하다.
  그래서 조회를 두 번 한다. 두 조회는 서로 독립이라 병렬로 보내며 실측
  0.3~0.8초짜리 요청 한 건이 추가된다.
- ① 계열로 교체하는 필드는 `open_qty`와 그 금액 환산 `open_amt` **둘뿐**이다.
  `po_qty`(PO 수량)·`pnfm_qty`(PNFM 수량)는 미입고가 아니라 PO 단위 총계이므로
  전체 창 값을 유지한다. 유지 필드는
  `pnfm_confirmed_qty`·`inbound_in_progress_qty`·`completed_qty`·`trouble_qty`·
  `po_qty`·`pnfm_qty`와 모든 식별 컬럼이다.
- 두 조회를 잇는 상품코드 매칭은 **정확 일치 우선, 대소문자만 다른 코드는 양쪽
  모두 모호하지 않을 때만** 연결한다. 실측에서 CMS가 같은 상품을 두 조회에서
  `KOEP05-FP`/`KoeP05-FP`로 다르게 반환한 사례가 1건 확인됐다. 이는 승인된 V3
  식별 정책(`V3_CASE_INSENSITIVE_CODE_EXACT_PRODUCT_NAME_PRESERVE_SUFFIX_V3`)과
  같은 방향이며, 한쪽에 대소문자만 다른 코드가 둘 이상이면 추측해 묶지 않고
  미연결로 남겨 ① 수량을 잃지 않는다.
- 소비 추적은 **최근 창 코드 기준 한 곳**에서만 한다. 전체 창 행의 fold 키로도
  함께 막으면, 모호한 fold가 뒤따르는 정확일치를 차단하고 최근 창 행이 별도 행으로
  append되어 ②③이 이중계상된다(아래 감사 결함 2).
- 미연결로 남은 최근 창 행(구제 행)은 전체 창에 같은 fold의 상품이 **있는 경우**
  ②③④·`trouble_qty`를 0으로 비운다. 그 상품의 ②③④는 이미 전체 창 행이 들고
  있으므로 구제 행의 역할은 ① 수량 보존뿐이다. 전체 창에 아예 없는 상품(진짜
  시점 드리프트)은 원래 값을 유지한다.

### 캐시·감사·버전

- PL·USA V3 재고 스냅샷 `cache_scope`는 `unreceived_cache_scope()`가 만든다
  (현재 `v3_inventory_position_unreceived_po_30d_v3`). **캐시 키에는 창 길이가
  들어가지 않으므로**(`_cache_key`는 version/entity/as_of/date_from/date_to/
  logistics_date_from/cache_scope만 해시) 창 길이를 scope에 접어 넣었다.
  `V3_UNRECEIVED_LOOKBACK_DAYS`를 바꾸면 scope가 함께 바뀌어 이전 창으로 받아둔
  스냅샷이 재사용되지 않는다. 이 장치가 없으면 45일로 바꿔도 30일 스냅샷이
  그대로 나온다(아래 감사 결함 1).
- HQ V3 재고 캐시(`v3_hq_inventory_position_guide_6m_v2`)는 **창 적용 전 전체
  수량**을 그대로 담고, 창은 캐시를 읽은 뒤 적용한다. 기존 캐시를 계속
  재사용할 수 있고 창을 다시 조정할 때 재조회가 필요 없다.
- 적용된 창은 `source_audit.unreceived_window`로 결과에 남는다(`version`,
  `basis=PO_REGISTRATION_DATE`, `date_from`, `date_to`, `calendar_days=30`,
  `scope=UNRECEIVED_OPEN_PO_QUANTITY_ONLY`). 법인별 적용 결과는
  `source_audit.inventory_source`에 남으며, HQ는 `zeroed_rows`/`zeroed_quantity`/
  `unparsable_date_rows`, PL·USA는 `changed_rows`/`case_only_code_matches`/
  `recent_only_rows`/`rescued_rows_with_preserved_fields_zeroed`/
  `blocked_negative_rows`/`blocked_negative_quantity`를 포함한다. HQ도
  `blocked_negative_rows`/`blocked_negative_quantity`를 함께 남긴다.
- `source_audit.unreceived_window`는 `as_of`만으로 결정되므로 **어느 payload가
  창 적용본인지 증명하지 못한다.** 적용 사실은 법인별 fetch 감사값
  (`zeroed_rows`/`changed_rows`)으로 확인해야 한다.
- 같은 창이 `snapshot_id` digest에도 들어가므로, 창 정책이 바뀌면
  `source_snapshot_id`도 바뀐다.
- 로직 버전은 `v3.26-web-demand-91d-separated` → **`v3.27-unreceived-po-30d`**,
  결과 schema는 기존 **`24`**를 유지한다. 행 구조가 바뀌지 않으므로 Excel
  내보내기 하위호환 가드도 그대로다.
- 과거 완료 결과는 소급 변환하지 않는다. 사라졌던 SKU 복구는 이 버전으로
  **재분석**해야 확인된다.

  않는다. 강화 산식이 승인되기 전까지 이 한 항목은 해설서 방향만 반영된 미결이다.
- SES/HOLT/Croston의 `alpha=0.20`, HOLT `beta=0.10`, `phi=0.90`을 사용한다.
  최초 판매 168일 이내 여부는 감사정보로만 남기며 모든 SKU의 HOLT `phi`는 0.90이다.
- 기존 V3 전용 `최근 84일 무판매 보류`와 `Croston 최근 3기 평균×2 상한`은
  해설서에 없으므로 제거한다. 전체 13주가 0이거나 Croston의 유효 판매 주가 2개
  미만인 경우처럼 엔진 계산 자체가 불가능한 경우는 계속 계산 차단한다.
- 쇼티지·현금흐름 모두 수요엔진과 무관하게 각 `시나리오×매출등급` Z를 사용한다.
  Croston도 쇼티지 시나리오를 현금흐름 Z로 덮어쓰지 않는다.
- 리드타임은 직전 **6개월 완료 표본**을 사용한다. 해설서의 “10~20건” 범위와
  “10건 미만 fallback 필요”를 함께 적용해 최소 계산 가능 표본을 10건으로 두며,
  fallback 산식은 문서에 확정돼 있지 않으므로 10건 미만은 고정값·타 법인 값으로
  대체하지 않고 차단한다. PL/USA는 운송수단별 완료 Packing No, HQ는 완료 PO×SKU다.
- `R=28일=4주`는 유지한다. 안전재고 fence는 주 단위로 PL 2~13주, USA 2~8주,
  HQ 2~5주다. 실측 `L_days`와 `sigma_L_days`는 `/7`하여 주 단위 Layer 산식에 넣고,
  미래 계절지수는 실제 달력일 구간으로 가중한다.
- 순수 정기발주 `S=Layer1+Layer2+Layer3`, `Q_raw=max(0,S-IP)`를 유지한다.
  박스입수량·MOQ·주문배수·CEILING은 API 원천이 없어 적용하지 않으며,
  `final_order_quantity`는 계속 미확정이다.
- 로직 버전은 `v3.21-guide-weekly`, 결과 schema는 `24`다. 과거 완료 결과는
  소급 변경하지 않으며 새 계약을 보려면 재분석해야 한다.

## 최신 순수 정기발주 `(R,S)` 전환 승인 — 2026-09-01

사용자는 V2와 같은 순수 정기발주 방식으로 V3의 최종 발주판정을 변경하도록
승인했다. 기존 `IP < ROP` gate를 제거하고, 계산 가능한 모든 SKU에 대해 매
분석 시점의 원시 발주필요수량을 다음처럼 계산한다.

```text
ROP_reference = Layer 1 + Layer 2  # 계산근거용 참고값, 발주조건에는 미사용
S = Layer 1 + Layer 2 + Layer 3
Q_raw = max(0, S - IP)
need_order = Q_raw > 0
```

- `IP`가 ROP 이상이더라도 `S`보다 작으면 `S-IP`를 발주필요수량으로 산출한다.
  `IP>=S`일 때만 발주필요수량은 0이다.
- 예: Layer 1=180, Layer 2=210, Layer 3=420이면 참고 ROP=390, S=810이다.
  IP=600이면 과거 gate에서는 0이었지만 새 공식은 `810-600=210`이다.
  IP=900이면 `max(0,810-900)=0`이다.
- V3의 364일 수요창, 계절 제거·재적용, SES/HOLT/Croston, Croston 상한·Z,
  실측 L·sigma_L, 28일 R, 법인별 안전재고 fence, IP 구성과 기존 계산 차단은
  변경하지 않는다.
- 박스입수·MOQ·발주배수·낱개 올림은 새로 적용하지 않는다. API의
  `raw_order_quantity`는 소수 정밀도의 원시 필요량이며 최종 주문수량은 계속
  주문제약 미확정이다.
- 화면·Excel은 발주조건을 `IP<S`와 `Q=max(0,S-IP)`로 설명한다. ROP는 과거
  결과 대사와 Layer 1+2 확인을 위한 참고값으로만 표시한다.
- 로직 버전 `v3.20-pure-periodic-rs`, 결과 schema `23`. 과거 완료 결과는
  소급 재계산하지 않으며 새 기준의 화면·Excel을 사용하려면 V3를 다시 분석한다.

사용자는 USA 조회에 포함된 EU 표기 상품 3개를 확인한 뒤 “반대로 얘네도 제외해줘”라고

## 최신 Excel 수식 결과 연결 승인 — 2026-08-31

사용자는 첨부 `ESM_발주분석_결과보고서_2.xlsx`의 참고지표·발주 타이밍·

아래 결정은 이전 절의 해당 항목 `미산출` 설명과 월평균 반올림 방식을 대체한다.
V3 예측·계절지수·Layer·ROP·S·IP·원시 발주량·원화 발주금액 산식은 변경하지 않는다.

- 계산 단위/원천: 법인×SKU×선택 시나리오. 최근 완료 13주(월~일, 무판매 주 0)의
  V3 정상 유상 실제 판매를 사용하며 주평균=`13주 합계/13`, 주간σ=`STDEV.S(13개 주합계)`.
  28일 예측오차 σ를 주간σ로 환산하지 않는다. 원천 달력일 기준은 V3와 동일하다.
- 월평균=`ROUND(13주 합계/3,0)`. API `reference_monthly_sales`는 반올림한 값이며
  `/3` 원값은 `reference_monthly_sales_raw`에 별도 보존한다.
- MOI=`ROUND((현지가용+운송중)/월평균,1)`. 원본처럼 발주제안은 IP 누락도 검사하며,
  물류전망 MOI는 IP 없이 재고·판매만 유효하면 계산한다. 고갈주수는 같은 재고/주평균이다.
- 평균 여유=`MAX(0,ROUND((IP-ROP)/주평균,1))`.
  평균 발주일=`기준일+MAX(0,(IP-ROP)/주평균)*7`.
- `gap=MAX(0,IP-ROP)`, `a=V3 Z*실제 주간σ`, `d=주평균`일 때 보수적 원주수는
  `((SQRT(a²+4*d*gap)-a)/(2*d))²`. 구현은 작은 gap에서 소실오차를 줄이는 동치식
  `(2*gap/(SQRT(a²+4*d*gap)+a))²`을 사용한다(분자·분모가 모두 0이면 0).
  보수적 여유는 원주수를 소수 1자리 반올림하고, 조기경보일은 **반올림 전** 원주수×7일이다.
  일시 소수부는 API/Excel에 보존하되 Excel 표시는 날짜다. 분모 0/미계산 입력은 `–`.

  비고 ETA 매핑 포함), 없으면 실제 운송수단의 V3 실측 평균 LT+출고일. σL은 더하지 않는다.
  실측 LT가 없는 운송수단이나 출고일 누락은 ETA 미확인. V2 고정 LT를 가져오지 않는다.

  조정은 하지 않는다. HQ 국제 shipping은 해당없음.
- ETA 수량은 이번 주 월요일 이전, `[월요일+7*i, 월요일+7*(i+1))` 13주,

## 최신 Excel 양식 및 13주 참고지표 — 2026-08-31

## 최신 분석 중단 동작 — 2026-08-31

계산 중에는 `분석 중단` 버튼을 표시한다. 명시적 중단은 해당 사용자·법인의

## 4. 즉시 중단이 필요한 핵심 위험

아래 항목은 결정 없이 구현하면 발주량 방향이나 규모가 크게 달라질 수 있다.

### 4.1 달력월과 4주 기간의 충돌

교과서는 최근 13기간을 `1기간=4주`로 사용하지만 계절지수는 달력월 1~12를
사용한다. 4주 기간은 매년 364일이므로 달력월과 계속 어긋난다. 판매 이력의
예측 grain, 달력월 시즌팩터, 일 단위 리드타임·검토기간을 어떻게 변환·합산할지
확정하지 않으면 같은 SKU도 실행일에 따라 다른 달 팩터가 잘못 연결될 수 있다.

기간창을 혼동하지 않는다.

- V3 교과서의 `13기간` = `13 × 4주` = 52주 = 364일, 약 1년
- V2의 `13주` = 13개 완료 주, 약 3개월
- V3 시즌팩터 관측창 `rolling 24개월` = 약 2년

즉, V3 예측엔진용 13기간과 시즌팩터 생성용 24개월은 목적과 grain이 다른 두
개의 데이터 창이다.

**사용자 결정(2026-08-27):** HQ·PL·USA의 SKU별 SES/HOLT/Croston 입력은
완료된 4주 구간 13개, 총 364일을 사용한다. 기능구분별 시즌팩터 생성은 완료된
달력월 기준 rolling 24개월을 별도 관측창으로 사용한다. 두 관측창을 하나로
합치거나 `13기간=2년`으로 해석하지 않는다. 과거 판매는 일자별로 해당 달의
시즌팩터를 나눈 뒤 4주 구간으로 집계한다. 비정상·부분기간 처리 세부는 아직
미결이다.

**사용자 결정(2026-08-28, 2026-08-27 시간대 결정을 대체):** CMS `출고일`은
법인·창고 시간대로 변환할 타임스탬프가 아니라 이미 확정된 **원천 달력일**이다.
HQ·PL·USA 모두 해당 날짜를 그대로 사용하고 창고별 시간대 마스터, UTC 변환,
DST 보정을 사용하지 않는다. 4주 구간은 날짜 기준 월요일부터 일요일까지이며,
실행 직전 완료 일요일을 기준으로 최근 13개 완료 구간을 역산한다.

**사용자 결정(2026-08-27):** 예측 기준일은 별도 고정일을 두지 않고,
실행 시점 직전의 완료된 일요일을 기준으로 한다. 해당 일요일에 종료된
4주 구간을 가장 최근 구간으로 삼아 최근 13개의 완료된 4주 구간을
역산한다. 실행 시점 이후의 거래나 아직 종료되지 않은 현재 구간은
예측 입력에서 제외한다.

**사용자 결정(2026-08-27):** V3의 수요 관측기간과 4주 구간은 영업일이
아닌 연속된 달력일을 기준으로 계산한다. 따라서 주말을 제외하거나 영업일
수로 보정하지 않으며, 4주 구간은 주말을 포함한 28일이다.

### 4.2 시즌팩터 규칙의 결합 방식

교과서는 다음을 사실상 운영값처럼 제시한다.

- `S(m) = 월평균 / 연평균`
- 축소추정 `w = n / (n + 30)`
- 통계적으로 계절성이 확인되지 않으면 `1.0`
- 미래 한 기간 또는 다음 기간의 월 팩터를 재적용

사용자 결정에 따라 위 식을 적용하되, 기존의 달력일 가중 결정과 다음처럼
결합한다. 판매 마감일 직전 완료월에서 끝나는 24개 완료월을 이전 12개월과 최근
12개월로 나누고, 각각 `1:2` 가중으로 달력월 평균과 전체 월평균을 만든다.
절대 연도는 고정하지 않는다. 이어서 `w=n/(n+30)`로 상위지수와 축소보정한다.
미래 Layer 1·3은 각각 `f1`,`f2`, Layer 2는 `L+R` 전체의 달력일 가중 `fLR`를
d̄와 σ에 동일 적용한다. 명시적으로 계절성 미확인 판정을 받은 조합만 1.0이며,
데이터 누락·계산실패·타 법인 누락을 1.0으로 숨기지 않는다. 남은 위험은 `n`
모집단과 계절성 확인 판정식이 교과서에 없다는 점이다.

### 4.3 서비스레벨 설명의 수치 오류 가능성

교과서는 `Z=1.68`을 서비스레벨 95.4%라고 하면서 동시에 “100번 중 0~1번
부족”이라고 설명한다. 표준정규 단측 확률 기준 `Z=1.68`은 약 95.35%이므로,
독립된 100회 보충주기라면 기대 부족주기는 약 4.65회다. “0~1회”를 목표로 한
것이라면 Z 또는 서비스레벨 정의가 다르다. 이 문구를 그대로 정책 설명이나
화면에 쓰면 경영진이 허용한 품절위험과 실제 계산이 다를 수 있다.

### 4.4 테스트베드가 완전한 계산 오라클이 아님

테스트베드는 안정형 SES만 13기간 원자료에서 즉시 반복 계산한다. 설명파일은
HOLT+감쇠와 Croston+SBA가 초기값에 따라 달라져 교과서 확정값을 편집 가능하게
보여준다고 명시한다. 따라서 테스트베드와 숫자가 같다는 사실만으로 HOLT·Croston
구현이 맞다고 판정할 수 없다.

### 4.5 교과서로 확정된 초기화와 남은 예외

- HOLT는 최초 level=첫 관측값, 최초 trend=둘째−첫째로 확정한다.
- Croston은 첫 판매 전 0기간을 간격에서 제외하고 첫 관측 판매간격·첫 판매량으로
  초기화하며, 판매 발생 기간에만 `p`,`z`를 갱신한다.
- 전기간 0, 판매 1회, HOLT 불충분 이력 처리
- 이전 6기간 합이 0일 때 추세신호
- 평균 0일 때 CV²
- CV² 0.49 이상인 추세 후보의 SES 우회 규칙
- 신규 SKU·분류 불가 SKU의 **최초 수요값**

첫 두 항목은 교과서대로 구현한다. 뒤 네 예외는 교과서만으로
서로 다른 개발자가 같은 결과를 만들 수 없으므로 계산을 차단한다.

단, 신규 SKU의 **계절지수**는 차단 대상이 아니다. 교과서의 축소추정
`w=n/(n+30)`과 `최종지수=w×조합지수+(1−w)×상위지수`를 적용한다. 이 규칙은
계절지수를 정하는 규칙이며, 판매이력이 전혀 없는 SKU의 최초 `d_bar`·`sigma`를
정하는 규칙은 아니다.

### 4.6 재고위치 중복계상

`운송중`, `미입고`, `입고예정`, `HQ가용`은 데이터 원천에 따라 같은 물량을
겹쳐 표현할 수 있다. 특히 HQ 재고가 아직 해당 법인에 예약·출고되지 않았다면
그 법인의 IP에 더하면 안 된다. PO/ASN/선적/입고 상태의 상호배타성과 기준시각을
먼저 계약해야 한다.

### V3-009 결정 — V2 리드타임 계약의 V3 기 단위 적용

**사용자 결정(2026-08-28):** V3의 실제 운영 `L`, `R`, `sigma_L`은 V2의
법인별 리드타임 정책과 원천 계약을 따른다. 단, V3의 수요 `d_bar`와 `sigma_d`는
4주 집계의 **기 단위**이므로 Layer 1·2·3에 넣는 `L`, `R`, `sigma_L`도 모두
`1기=4주=28일` 기준으로 환산한다. 주·일 단위 수치를 V3 기 단위 산식에 그대로
넣지 않는다.

| 법인 | V2 정책 운송수단 | `R` (V3 기 단위) | `L`·`sigma_L` 원천 및 V3 환산 |
| --- | --- | ---: | --- |
| PL | CASH=`RAIL`, SHORTAGE=`SEA` | `4주 ÷ 4주 = 1.0기` | 시나리오 운송수단별 최근 12개월 완료 Packing No 표본에서 `L_days=mean(ow_to_iw_days)`, `sigma_L_days=STDEV.S(ow_to_iw_days)`를 구한 뒤 각각 `/28`한다. |
| USA | CASH=`AIR`, SHORTAGE=`SEA` | `4주 ÷ 4주 = 1.0기` | PL과 같은 완료 Packing No 집계·환산 규칙을 AIR와 SEA에 각각 적용한다. |
| HQ/OPO | CASH·SHORTAGE 모두 국내조달 공통 | `28일 ÷ 28일 = 1.0기` | 최근 12개월 완료 `PO×SKU` 표본의 `actual_received_at - po_created_at` 일수 평균과 `STDEV.S`를 구한 뒤 각각 `/28`한다. 두 시나리오는 `L`·`sigma_L`이 같고 Z만 다르다. |

PL·USA는 V2의 완료 Packing No dedup·충돌 Packing 제외, `1~180일` 유효기간,
운송수단별 최소 유효 표본 2건 규칙을 그대로 따른다. HQ도 최근 12개월 유효 완료
`PO×SKU` 표본이 2건 미만이면 계산을 차단한다. 세 법인 모두 표본 부족·원천 실패를
교과서 고정값이나 임의값으로 대체하지 않는다. 실행 snapshot에는 원천의 일 단위
평균·표준편차·표본 수와, 실제 Layer 계산에 사용한 기 단위 `L`·`R`·`sigma_L`을 함께
남긴다.

손검산 예시: PL 쇼티지 해운 실측이 `L=72.9일`, `sigma_L=2.18주`라면 V3에는
`L=72.9÷28=2.604기`, `R=4÷4=1.000기`,
`sigma_L=(2.18×7)÷28=0.545기`를 사용한다.

Layer 2 안전재고 fence도 V2의 법인별 업무정책을 유지한다. V3에서 Layer 2에
적용하는 계절 재적용 평균수요를 `d_bar_L2`라고 하면 다음과 같다.

```text
SS = MIN(MAX(SS_raw, d_bar_L2 × SS_floor_periods),
         d_bar_L2 × SS_cap_periods)
```

| 법인 | V2 fence | V3 `SS_floor_periods` | V3 `SS_cap_periods` |
| --- | --- | ---: | ---: |
| PL | 2주 ~ 13주 | `2÷4 = 0.5기` | `13÷4 = 3.25기` |
| USA | 2주 ~ 8주 | `2÷4 = 0.5기` | `8÷4 = 2.0기` |
| HQ/OPO | 14일 ~ 35일 | `14÷28 = 0.5기` | `35÷28 = 1.25기` |

따라서 `d_bar`가 기당 수요인 V3에서 PL의 적용값은
`SS=MIN(MAX(SS_raw, d_bar_L2×0.5), d_bar_L2×3.25)`다. `×2`, `×13`을
그대로 쓰면 각각 2주·13주가 아니라 2기·13기가 되어 V2 fence보다 4배 넓어지므로
사용하지 않는다.

### V3-014 결정 — 실측 소수 리드타임의 HOLT·계절 구간 처리

**사용자 결정(2026-08-28):** V2 실측 `L`이 `72.9일=2.604기`처럼 소수일·소수기가
될 수 있으므로, HOLT를 `L=R=1기` 교과서 예시에만 제한하지 않는다. 미래 28일
기간별 HOLT 예측을 실제 Layer 날짜구간과 겹치는 기간 비율만큼 합산한다. 소수일과
소수기는 반올림하지 않는다.

```text
HOLT Layer1 = Σ(미래 28일 기간별 예측 × [발주일, 발주일+L)과의 겹침 기 비율) × f1
HOLT Layer3 = Σ(미래 28일 기간별 예측 × [발주일+L, 발주일+L+R)과의 겹침 기 비율) × f2

HOLT Layer2용 d_bar =
  (Σ(미래 28일 기간별 예측 × [발주일, 발주일+L+R)과의 겹침 기 비율) ÷ (L+R 기)) × fLR
```

`f1`, `f2`, `fLR`도 같은 실제 날짜의 반개구간 `[start, end)`로 계산한다. 월
경계에 걸친 소수일은 해당 달 팩터에 소수 일수만큼 가중하며, 날짜를 반올림해
다른 달로 보내지 않는다. 이 규칙은 유효·승인된 시즌팩터가 입력되었다는 전제의
순수 계산 규칙이며, 팩터 누락·오류를 `1.0`으로 대체하는 승인은 아니다.

### V3-015 결정 — 영업일 vs Calendar Day

**사용자 결정(2026-08-28):** V3 웹 발주 로직의 리드타임과 모든 기간 계산은

### V3-016 결정 — 최근 판매 없음 보류와 Croston 상한

**사용자 결정(2026-08-28):** 분석 기준일 직전의 완료된 84 Calendar Days,

영업일 보정은 사용하지 않는다.

간헐형으로 분류되어 Croston+SBA를 선택한 SKU에는 다음의 상한을 적용한다.

cap = mean(최근 3개 완료 28일 기간의 계절 제거 수요) × 2

상한은 Croston의 `d_bar`, 다음 기 점예측과 Layer 1·2·3 수요에 적용한 뒤,

`10, 20, 30`이면 `cap=(10+20+30)/3×2=40`이며, Croston 점예측 `55`는 `40`으로
제한한다. `30`이면 제한하지 않는다.

않는다. 결과 행에는 네 구성요소를 각각 남겨 IP를 대사할 수 있게 한다.

법인별 문제재고 정책도 V2를 그대로 계승한다. HQ/OPO는 V2가
`stock_status=trouble`인 재고를 가용재고 합산 전에 제외한다. PL·USA는 V2가
CMS의 `avbl_qty`를 가용수량으로 사용하므로 V3도 별도 `TROUBLE` 창고명 또는
`trbl_yn` 필터를 추가하지 않는다. 즉 PL·USA의 해당 제외 여부는 `avbl_qty` 원천
정의에만 의존한다.

### V3-004 참고 — V2의 현재 판매수요·대량주문 처리

V3 판매 모집단을 결정할 때 비교 기준으로 사용할 V2의 현재 동작은 다음과 같다.

- PL·USA는 현재 주를 제외한 직전 13개 완료 주, HQ는 현재일을 제외한 직전
  91개 완료일을 수요 표본으로 사용한다.
- PL·USA의 완료 주는 문서상 `Monday–Sunday`이므로 토요일·일요일을 포함한다.
  HQ의 91개 완료일 창에도 주말 제외 또는 평일만 집계하는 규칙은 명시되어
  있지 않으므로, 거래유형 필터를 통과한 주말 판매는 수요에 포함된다.
- 법인별 허용 거래유형의 정상 출고수량을 포함한다. 정상 양수
  `SELF(자사간거래)`도 포함한다.
- 직원판매, `FREE SAMPLE` 등 무상샘플, 반품, 추후상계·회계조정 거래행은
  거래유형 필터에서 제외한다.
- `amount < 0 AND qty > 0`인 확인된 사고처리 형태는 수요수량과 Pareto 매출에서
  제외하고 건수·수량·금액·거래유형 분포를 감사정보에 남긴다.
- 프로모션을 식별하는 원천 필드나 자동 제외 규칙은 없다. 허용 거래유형의 정상
  양수 판매라면 프로모션 판매도 일반 수요에 포함된다.
- 대량주문도 수요에서 제외하거나 cap하지 않는다. PL·USA는 한 주 최대 판매량이
  `판매가 있었던 주의 평균 × 3`을 초과하면 `대량포함`으로 표시한다. HQ는 같은
  기준을 일 단위로 적용한다.
- `대량포함`은 검토 신호다. 해당 판매량은 13주/91일 평균과 표준편차, Pareto와
  최종 발주량 계산에 그대로 남는다. API의 `data_status`·`has_bulk_week`, 화면의
  데이터 상태, Excel의 `상태` 열에서 확인할 수 있다.
- 화면 fixture의 “현지 프로모션 물량 추가” 메모는 사용자 검토 예시이며,
  프로모션을 자동 감지하거나 수요를 자동 가감하는 운영 기능은 아니다.

따라서 V3-004에서 프로모션·대량주문을 제외하려면 V2를 그대로 계승하는 것이
아니라 새로운 정책을 명시적으로 승인해야 한다.

**사용자 배경 설명(2026-08-27):** 현재 원천으로는 어떤 판매가 행사·프로모션
때문인지 전부 파악할 수 없다. 이것이 V2에서 프로모션·대량주문을 수요에서
자동 제외하지 않은 이유다. 따라서 이력의 크기나 통계적 이상치만으로 행사라고
단정해 제거하면 정상 성장·정상 대량주문을 누락할 위험이 있다. 이 설명은 V2
정책의 근거이며 V3에도 같은 원칙을 적용한다.

**사용자 결정(2026-08-27):** 확실한 행사 구분 근거가 없는 정상 판매와
대량주문은 V3 공식 수요에서 자동 제외하지 않는다. 원본 판매량을 공식 수요에
포함하고 대량 신호를 별도로 표시한다. 포함·제외 시 결과 차이는 참고용 민감도
정보로 제공할 수 있지만, 통계적 크기만으로 공식 수요를 바꾸지 않는다. 사용자가
일회성 행사로 확인해 수동 분리하는 경우에는 대상, 수량, 사유, 사용자, 시각을
감사정보에 남긴다. 향후 신뢰할 수 있는 행사 원천 필드가 생기면 별도 승인 후
자동화한다.

**사용자 결정(2026-08-27):** 법인간 출고도 출고 법인의 공식 수요에 포함한다.
따라서 HQ에서 PL·USA로 보낸 출고는 HQ 수요에 포함하고, PL·USA의 판매수요는
각 법인에서 별도로 계산한다. 동일 물량이 법인별 단계에 각각 나타나는 것은 각
재고거점의 보충수요이므로 허용하지만, 법인별 결과를 합쳐 하나의 전사 수요로
다시 계산하지 않는다. 법인간 거래 여부를 식별하는 원천 필드는 감사·민감도 분석을
위해 보존한다.

**사용자 결정(2026-08-27):** 반품 거래행은 V3 공식 수요에서 제외한다.
원천에서 반품으로 식별된 행의 수량을 정상 판매에 음수로 합산하지 않으며,
제외 건수·수량과 거래유형을 감사정보에 남긴다. 단순 음수수량을 모두 반품으로
추정하는 규칙은 승인하지 않았으므로, 실제 반품 식별 필드·코드는 원천 계약에서
확정해야 한다.

**사용자 결정(2026-08-27):** `FREE SAMPLE` 등 무상샘플 거래행은 V3 공식
수요에서 제외한다. 다만 상품명이나 SKU 속성이 샘플·사쉐·샤쉐라는 이유만으로
상품을 제외하지 않으며, 법인별 허용 거래유형으로 발생한 정상 유상 판매수량은
다른 상품과 동일하게 포함한다. 제외 건수·수량·거래유형은 감사정보에 남긴다.

**사용자 결정(2026-08-27):** 원천에서 취소로 식별된 주문·거래행은 V3 공식
수요에서 제외한다. 취소 상태를 정상 판매수량에 포함하거나 음수로 상계하지 않으며,
제외 건수·수량·상태코드를 감사정보에 남긴다. 실제 취소 식별 필드와 상태코드는
원천 계약에서 확정한다.

**사용자 결정(2026-08-27):** `금액 < 0`이면서 `수량 > 0`인 행은 확인된
사고처리 형태로 보고 V3 공식 수요수량과 Pareto 등급 매출, 시즌팩터 원천에서
모두 제외한다. 원본 판매내역과 재무용 순매출은 보존하고, 제외 행 수·영향 SKU 수·
수량·금액·거래유형 분포를 감사정보에 남긴다. 이 형태를 넘어선 다른 사고처리
식별 규칙은 원천 근거와 별도 승인 없이 추가하지 않는다.

**사용자 결정(2026-08-27):** 배송비·수수료 등 원천에서 비실물로 식별된 항목은
V3 공식 수요와 시즌팩터, 계산대상 상품 모집단에서 제외한다. 제외 항목 수·수량·
금액·상품유형을 감사정보에 남긴다. 상품명 문자열만으로 비실물을 추정하지 않고,
승인된 상품유형·코드·마스터 필드를 사용하며 실제 식별 계약은 원천 연동 전에
확정한다.

**사용자 결정(2026-08-27):** 판매행 중복은 백테스트 원천에서 실제 중복 후보와
사용 가능한 고유키의 완전성·유일성을 먼저 조사한다. 안정적인 판매행 고유 ID가
확인되기 전에는 날짜·법인·SKU·수량·금액이 같다는 이유만으로 행을 삭제하지
않고 후보 건수와 영향 수량을 경고·감사정보로 남긴다. 조사 결과를 검토한 뒤
dedup 키와 중복 처리 방식을 별도로 확정한다.

## 9. 프로젝트 작업 규칙

1. V3 전체 로직을 수정·검토하기 전에 이 문서를 끝까지 읽는다.
2. 시즌팩터를 건드릴 때는 `ORDER_V3_SEASON_FACTOR_SPEC.md`도 끝까지 읽는다.
3. 문서의 예시 숫자, 테스트베드 값, 프런트 fixture를 운영 기본값으로 복사하지
   않는다.
4. 기술명세에 없는 산식·상수·fallback을 추정하지 않는다.
5. 발주수량에 영향을 주는 코드 전에 자연어 계산 계획과 손검산 예시 1~2개를
   제시하고 사용자 승인을 받는다.
6. 기존 발주분석, V2, V3의 순수 산식·원천 매핑·서비스·API·화면·Excel 경계를
   유지한다.
7. 월간 시즌팩터 사전계산과 웹 요청 시 V3 발주계산을 분리한다.
8. 프런트에서 운영 산식을 계산하거나 팩터·계수를 하드코딩하지 않는다.
9. 백엔드의 순수 계산 모듈을 단일 원천으로 만들고 API·화면·Excel은 같은 실행
   결과를 사용한다.
10. 원본 CMS 판매행, API 키, 사용자 데이터, 민감 집계를 저장소·fixture·로그에
    기록하지 않는다.
11. 금액·단가·Excel 열은 기존 권한 정책을 통과시킨다.
12. 실행마다 원천 기준시각, 로직 버전, 계수 버전, 시즌팩터 버전, L/R/Z,
    분류 결과, fallback 사유를 재현 가능하게 남긴다.
13. 사용자 수량수정·보류는 변경 전후 값, 사유, 사용자, 시각을 남긴다.
14. dirty worktree의 기존 사용자 변경을 보존하고 관련 없는 파일을 정리하거나
    커밋에 섞지 않는다.
15. 테스트 통과만으로 계산이 맞다고 선언하지 않는다. 대표 SKU 손계산,
    API·화면·Excel 대사, 과거기간 백테스트를 함께 수행한다.
