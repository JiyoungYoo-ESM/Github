# ESM SCM main 브랜치 코드 분석 정리

작성 기준: `main` 브랜치, `origin/main` 최신 상태  
작성 목적: 팀장님 및 외부/다른 AI가 현재 웹사이트의 목적, 화면 구성, 데이터 흐름, 핵심 산식, 코드 평가 포인트를 빠르게 이해할 수 있도록 정리

---

## 1. 한 줄 요약

이 웹사이트는 실리콘투 ESM/SCM 업무에서 CMS 판매·재고·운송·미입고 데이터를 기반으로 발주 필요 SKU, 재고 공백 위험, 국가/브랜드/SKU/성분별 수요 인사이트, 시즌성, 보고서 생성을 한곳에서 분석하기 위한 내부 업무용 데이터 분석 웹앱이다.

---

## 2. 육하원칙 정리

### 누가

주 사용자는 ESM/SCM 실무자, BM, 브랜드/국가 담당자, 리더/팀장급 의사결정자다.

사용자별로 보는 관점은 다르다.

- SCM/ESM 실무자: 어떤 SKU를 언제, 얼마나 발주해야 하는지 확인한다.
- BM/브랜드 담당자: 브랜드별 판매 흐름, SKU 집중도, 시즌성, 재고 리스크를 확인한다.
- 국가/권역 담당자: 국가별 판매 비중, 성장률, 카테고리 수요를 확인한다.
- 팀장/리더: 발주 금액, 품절 위험, 인사이트 리포트, 데이터 품질 이슈를 종합해서 판단한다.

### 언제

업무 기준일 또는 CMS 조회 기준일을 지정해 분석한다.

- 발주 분석은 기준일의 재고, 판매, 운송중, 미입고 상태를 기준으로 수행된다.
- 인사이트 분석은 선택한 기간의 판매 이력과 상품 마스터를 기준으로 수행된다.
- 시즌/수요 분석 API는 최소 `2015-01-01` 이후 데이터만 허용하고, 직접 선택 범위는 최대 24개월로 제한한다.

### 어디서

프론트엔드는 Next.js, 백엔드는 FastAPI다.

- 프론트엔드: `ESM_SCM8/frontend`
- 백엔드: `ESM_SCM8/backend`
- 분석 엔진: `ESM_SCM8/core`
- 주요 통합 화면: `frontend/components/redesign/SiliconAnalyticsWorkspace.tsx`

### 무엇을

크게 두 종류의 업무를 수행한다.

1. 발주 정량 분석
   - 데이터 입력
   - 데이터 진단
   - 발주분석
   - 재고 공백
   - 최종 발주 후보 확정

2. 수요/인사이트 분석
   - 인사이트 데이터 입력
   - 국가 분석
   - 브랜드 분석
   - SKU 분석
   - 성분 분석
   - 시즌 캘린더
   - 교차분석
   - 브랜드 자동 리포트

### 어떻게

CMS API 또는 업로드 파일을 통해 원천 데이터를 가져온 뒤, pandas 기반 분석 엔진에서 SKU 단위로 데이터를 통합한다.

발주 분석은 다음 흐름으로 계산된다.

1. EU 현지 재고, 본사 EU 창고 재고, 판매내역, 본사→EU 출고내역, 운송중, 미입고 데이터를 읽는다.
2. SKU 기준으로 상품명, 브랜드, 재고, 판매량, 운송중 수량, 미입고 수량을 병합한다.
3. 최근 3개월 판매량으로 월평균/일평균 판매속도를 계산한다.
4. 현지 재고와 운송중 재고가 안전재고 목표수량을 만족하는지 계산한다.
5. 부족하면 발주 필요 수량과 금액을 산출한다.
6. ETA가 고갈 예상일보다 늦으면 입고 전 결품 위험을 표시한다.
7. 결과를 화면, 엑셀 다운로드, 대시보드, 재고 공백 화면에 재사용한다.

인사이트 분석은 다음 흐름으로 계산된다.

1. CMS 판매 이력과 상품 마스터를 가져온다.
2. 상품코드, 브랜드, 상품명, 카테고리, 국가, 고객, 성분 키워드를 정규화한다.
3. 월별, 국가별, 카테고리별, 브랜드별, SKU별, 성분별 집계를 만든다.
4. 성장률, 비중, 피크월, 상위 SKU, 매핑 품질을 화면별로 보여준다.

### 왜

기존에는 발주 판단을 위해 여러 CMS/ERP 파일을 사람이 수작업으로 맞춰야 했을 가능성이 크다. 이 시스템은 그 과정을 자동화해 아래 문제를 줄이려는 목적이다.

- SKU별 발주 필요 여부 판단 시간 단축
- 현지 재고, 운송중, 미입고, 판매속도를 한 기준으로 통합
- ETA 이전 품절 가능 SKU 선제 파악
- 브랜드/국가/SKU/성분 단위 수요 흐름 시각화
- 보고서 작성 자동화
- 데이터 누락, 매핑 오류, 0단가, 미분류 SKU 등 품질 이슈 조기 발견

## 3. 전체 기술 구조

### 프론트엔드

- Next.js App Router 기반
- TypeScript/React
- UI 아이콘: `lucide-react`
- 차트: `recharts`
- 엑셀 내보내기 일부: `xlsx`
- 핵심 통합 업무 화면: `SiliconAnalyticsWorkspace`

### 백엔드

- FastAPI
- pandas 기반 분석
- 업로드 분석 API: `/api/analyze`
- CMS 기반 발주 분석 API: `/api/analyze/cms`
- 시즌/수요 분석 API: `/api/season-trend/analyze-api`
- 결과 다운로드 API: `/api/download/{job_id}`
- 최근 분석 결과 저장/조회 기능 포함

### 분석 엔진

주요 파일:

- `core/order_review.py`: 발주 필요 수량, 금액, 상태, ETA 위험, 운송 추천 계산
- `core/order_review_data.py`: SKU 기준 집계, 단가 산출, 마스터 SKU 구성
- `core/kpi.py`: 대시보드 KPI, 환율, 공급 파이프라인 금액 계산
- `core/season_calendar.py`: 월별/국가별/카테고리별 수요 집계
- `core/ingredient_trend.py`: 성분 키워드 기반 트렌드 집계
- `backend/analysis.py`: 업로드/CMS 데이터를 분석 엔진에 연결하고 화면 응답/엑셀 결과 구성

## 5. 데이터 입력 방식

### 발주 분석 데이터 입력

프론트 함수:

- `analyzeFromCms(asOf, options)`
- `analyzeFiles(filesByRole, options)`
- `analyzeFileList(files, roles, options)`

백엔드 API:

- `/api/analyze/cms`
- `/api/analyze`

입력 가능한 주요 옵션:

- `eur_krw_rate`: EUR/KRW 환율
- `safety_months`: 안전재고 개월 수
- `local_target_months`: 현지 목표 개월 수
- `transport_target_months`: 운송 목표 개월 수
- `sku_shortage_threshold_pct`: SKU 집중도 부족 판단 임계값
- `sku_overstock_threshold_pct`: SKU 집중도 과잉 판단 임계값
- `lead_time_air`: 항공 리드타임
- `lead_time_sea`: 해운 리드타임
- `lead_time_rail`: 철송 리드타임
- `lead_time_truck`: 트럭 리드타임

발주 분석에 쓰는 데이터 역할:

- `eu_stock`: EU 현지 재고
- `hq_eu_stock`: 본사 EU 창고 재고
- `sales_detail`: EU 판매 상세
- `hq_to_eu_sales_detail`: 본사→EU 출고 상세
- `shipping`: 운송중/ETA 데이터
- `open_po`: 미입고/오픈 PO
- `sales_history`: 장기 판매 이력
- `prod_list`: 상품 마스터
- `category_correction`: 카테고리 보정값

### 인사이트/시즌 분석 데이터 입력

백엔드 API:

- `/api/season-trend/analyze-api`
- `/api/season-trend/analyze`

필수 데이터:

- `sales_history`
- 선택/보조: `prod_list`, `category_correction`

분석 옵션:

- `start_date`
- `end_date`
- `metric`: `qty` 또는 `amount`
- `group_by`: `month`, `quarter`, `year`

- `exclude_partial_months`

## 6. 분석 결과 데이터 흐름

### 발주 분석 결과 생성

`backend/analysis.py`의 `run_core_analysis_from_uploaded_data()`가 중심이다.

처리 흐름:

1. 업로드 또는 CMS에서 받은 데이터를 `SessionContext`에 저장한다.
2. 기본 설정을 만들고 사용자가 입력한 환율/목표개월/리드타임을 반영한다.
3. `order_review_df()`로 SKU 단위 발주 검토 결과를 만든다.
4. 제외 SKU와 정상 검토 SKU를 나눈다.
5. 화면용 리포트 테이블, 확인필요 테이블, 재고 ETA 테이블, SKU 집중도 테이블을 만든다.
6. 시즌/성분 분석 결과도 가능한 경우 함께 만든다.
7. 엑셀 결과 파일을 생성하거나 CMS 분석에서는 지연 생성한다.
8. 프론트에 `summary`, `tables`, `season_analysis`, `ingredient_analysis`, `download_url`을 반환한다.

### 프론트 저장 및 재사용

프론트에서는 최근 분석 결과를 저장하고 여러 화면에서 재사용한다.

- 발주분석 화면은 `getOrderReviewRows()`
- 재고 공백 화면은 `getStockGapItems()`
- 인사이트 화면은 `getSeasonTrendAnalysis()`
- 글로벌 검색은 발주/재고공백/국가/브랜드/SKU/교차/리포트 데이터를 모아 검색 후보를 만든다.

## 7. 발주 분석 핵심 산식

### 기본 판매속도

기준 판매량은 최근 3개월 판매수량이다.

```text
월평균 판매수량 = 최근 3개월 판매수량 / 3
일평균 판매수량 = 최근 3개월 판매수량 / 90
```

### 확보 재고

```text
유럽+운송 수량 = EU 현지 가용수량 + 운송중 수량
```

### 안전재고 개월 수

사용자가 설정한 안전재고 개월 수를 발주 목표의 단일 기준으로 사용한다. 기본값은 3개월이다.

### 목표 수량

```text
안전재고 목표수량 = 월평균 판매수량 × 안전재고 개월 수
```

### 커버 가능 기간

```text
EU 현지 커버일수 = EU 현지 가용수량 / 일평균 판매수량
커버가능 개월수 = EU 현지 가용수량 / 월평균 판매수량
운송 포함 보유개월수 = (EU 현지 가용수량 + 운송중 수량) / 월평균 판매수량
계산 반영 보유개월수 = 계산 반영 수량 / 월평균 판매수량
```

판매량이 0이면 화면에서 사실상 충분 또는 판매없음 처리를 위해 큰 값(`999`, `99`)을 넣는다.

### 고갈 예상일

```text
고갈 예상일 = 기준일 + min(EU 현지 커버일수, 999)일
```

판매량이 없으면 `판매없음`으로 처리한다.

### 발주 필요 수량

```text
1차 부족수량 = max(안전재고 목표수량 - 유럽+운송 수량, 0)
본사 이동 수량 = 0
추가 발주 필요 수량 = 1차 부족수량
최종 부족수량 = 추가 발주 필요 수량
발주필요수량 = 추가 발주 필요 수량
```

현재 main 기준 코드에서는 본사 이동 수량이 기본 0으로 들어가며, 실제 부족 수량 차감에는 적극 반영되지 않는다. 즉, 현재 발주 수량의 핵심은 `안전재고 목표수량 - (EU 현지 가용수량 + 운송중 수량)`이다.

### 발주 필요 금액

단가는 EU 입고단가를 기준으로 한다.

```text
EU 입고단가_EUR =
  EU 입고단가 통화가 KRW이면 원본 EU 입고단가 / EUR/KRW 환율
  EU 입고단가 통화가 EUR이면 원본 EU 입고단가

EU 입고단가_KRW =
  EU 입고단가 통화가 KRW이면 원본 EU 입고단가
  EU 입고단가 통화가 EUR이면 원본 EU 입고단가 × EUR/KRW 환율

추가 발주 필요 금액 = 추가 발주 필요 수량 × EU 입고단가_KRW
부족금액_EUR = 추가 발주 필요 수량 × EU 입고단가_EUR
부족금액_KRW = 추가 발주 필요 금액
```

### 0단가 제외

재고 파일에 존재하는 SKU인데 원본 EU 입고단가가 0 이하이면 `0단가/무상` 유형으로 발주 검토 제외 처리한다.

```text
조건:
재고파일 존재여부 = Y
AND 원본 EU 입고단가 <= 0
AND 정상 SKU 형식

결과:
제외 SKU = True
제외유형에 0단가/무상 추가
제외사유 = 입고단가 0, 무상제공/FOC성 SKU로 발주 검토 제외
```

### 발주 상태 판단

발주 제외 조건:

- 제외 SKU로 표시된 경우
- SKU등록상태가 정상등록이 아닌 경우
- 단가 미등록 플래그가 있는 경우
- 월평균 판매수량이 0 이하인 경우
- 월평균 판매수량이 최소 판매 기준 미만인 경우

확인필요 조건:

- Hold수량이 재고수량보다 큰 경우 등 데이터 오류 가능성이 있는 경우

정상 발주 필요 조건:

```text
추가 발주 필요 수량 > 0
```

정상 발주 불필요 조건:

```text
EU 현지 가용수량 + 운송중 수량이 안전재고 목표수량을 충족
```

### ETA 지연 플래그

```text
ETA 지연 플래그 = Y
조건:
운송중 수량 > 0
AND 최초 ETA 존재
AND 고갈 예상일 존재
AND 최초 ETA > 고갈 예상일
```

### 입고 전 결품 위험

`apply_pre_arrival_shortage_risk()`에서 계산한다.

```text
입고까지 남은 일수 = 최초 ETA - 기준일
입고 전 예상 결품량 = max(일평균 판매수량 × 입고까지 남은 일수 - EU 현지 가용수량, 0)
긴급 보충 필요 수량 = 입고 전 예상 결품량
입고 전 결품 위험 여부 = 입고 전 예상 결품량 > 0 이면 Y
```

권장 긴급 액션:

- 본사 EU 창고 재고가 긴급 필요 수량 이상이면 본사 EU창고 이동 검토
- 운송중 수량이 있으면 기존 운송건 일부 항공 전환 또는 ETA 앞당김 검토
- 운송중 수량이 없으면 신규 긴급 발주 검토

### 운송수단 검토

운송수단 검토는 고갈 예상일까지 남은 일수와 리드타임을 비교해 추천한다.

```text
고갈까지 남은 일수 = 고갈 예상일 - 기준일
운송수단 검토안 = transport_recommendation_by_depletion_days(고갈까지 남은 일수, 리드타임)
예상 도착 가능일 = 기준일 + 선택된 운송수단 리드타임
```

### 시간 기반 항공/철송/해운 배분

발주필요수량이 있고 일평균 판매량이 있을 때 90일 동안 재고 흐름을 시뮬레이션한다.

```text
각 일자 재고 = 전일 재고 - 일평균 판매수량 + 해당 일자의 ETA 입고수량

항공 필요 수량 =
  항공 리드타임 기간 안에서 재고가 음수가 되는 최소값의 절대값

철송 필요 수량 =
  min(잔여 발주수량, (철송 리드타임 - 항공 리드타임) × 일평균 판매수량)

해운 필요 수량 =
  발주필요수량 - 항공 필요 수량 - 철송 필요 수량
```

정수 반올림 후 합계가 발주필요수량을 초과하면 해운, 철송, 항공 순서로 차감한다.

## 8. 재고 공백 화면 산식

재고 공백 화면은 백엔드 발주 결과와 ETA 데이터를 프론트에서 다시 가공한다.

핵심 파일:

- `frontend/lib/stock-gap.ts`
- `frontend/components/redesign/SiliconAnalyticsWorkspace.tsx`

### 일평균 판매량

```text
일평균 판매량 = 최근 3개월 판매수량 / 90
```

단, 백엔드에서 `avgDailySalesQty`가 오면 그 값을 우선 사용한다.

### 재고 소진 예정일

```text
재고 소진 예정일 = 기준일 + floor(현재 가용재고 / 일평균 판매량)일
```

### 최초 ETA

ETA 목록에서 기준일 이후이고 운송중 수량이 0보다 큰 가장 빠른 ETA를 선택한다.

### 공백 일수

```text
공백 일수 = max(최초 ETA - 재고 소진 예정일, 0)
```

### 부족 수량

```text
부족 수량 = 공백 일수 × 일평균 판매량
```

화면에서는 긴급 보충, 주의, 정상, 확인 필요 상태를 나눈다.

긴급 보충에 가까운 조건:

- 이미 재고 공백이 진행 중
- 입고 전 결품 위험 플래그가 있음
- ETA 지연 플래그가 있음
- 공백 일수가 길거나 긴급 보충 수량이 있음

## 9. 발주분석 화면 산식

통합 워크스페이스의 발주분석 화면은 백엔드 결과를 다시 화면용으로 정렬/표시한다.

### MOI

MOI는 Month of Inventory 의미로 사용된다.

```text
MOI = (EU 현지 가용재고 + 시나리오상 미입고 반영 수량) / 월평균 판매수량
```

시나리오:

- `before`: 미입고 미반영
- `after`: 미입고 반영

```text
before MOI = EU 현지 가용재고 / 월평균 판매수량
after MOI = (EU 현지 가용재고 + 미입고수량) / 월평균 판매수량
```

### 미입고 반영 발주 수량

```text
before 발주수량 = 발주필요수량
after 발주수량 = max(발주필요수량 - 미입고수량, 0)
```

### 발주 단가와 금액

```text
발주 단가 =
  발주필요수량 > 0 AND 발주필요금액 > 0 이면 발주필요금액 / 발주필요수량
  아니면 unitPrice

조정 발주 금액 = 조정 발주 수량 × 발주 단가
```

### 상태 판단

```text
조정 발주 수량 <= 0 이면 충분
MOI < 1.5 또는 우선 액션에 긴급 포함이면 긴급
MOI < 2 또는 우선 액션에 권장 포함이면 주의
그 외 주의
```

### 정렬

발주분석 화면은 사용자가 선택한 정렬 기준에 따라 정렬한다.

- 권장 발주 금액 높은 순
- 발주 필요 수량 높은 순
- 고갈 위험 높은 순
- 판매속도 빠른 순

금액 정렬의 우선순위:

```text
조정 발주 금액 desc
조정 발주 수량 desc
MOI asc
```

- `core/kpi.py`

### 공급 파이프라인 KPI

```text
본사→EU 출고금액 = HQ-to-EU 판매/출고 상세의 금액 합계 × EUR/KRW 환율
```

## 15. SKU 분석 화면 역할과 산식

화면명: SKU 분석  
초기 화면 ID: `sku`

목적:

- 개별 SKU의 판매 추이, 피크월, 국가 분포, 카테고리, 재고 위험을 확인한다.

주요 산식:

```text
월별 SKU 판매수량 = SKU × 월 기준 판매수량 합계
월별 SKU 판매금액 = SKU × 월 기준 판매금액 합계
피크월 = 월별 판매수량 또는 판매금액이 가장 큰 월
국가별 SKU 비중 = 해당 SKU의 국가별 판매값 / 해당 SKU 전체 판매값 × 100
```

추천 발주월:

```text
추천 발주월 = ((피크월 + 9 - 1) % 12) + 1
```

즉, 피크월보다 약 3개월 앞선 월을 발주 준비 월로 보는 방식이다.

## 16. 성분 분석 화면 역할과 산식

화면명: 성분 분석

- 상품명/마스터의 성분 키워드를 기반으로 성분 트렌드를 분석한다.
- 어떤 성분이 어떤 국가/브랜드/SKU에서 성장하는지 본다.

성분 키워드:

- 기본 맵: `data/ingredient_maps/default_ingredient_map.json`
- 분석 로직: `core/ingredient_trend.py`

주요 집계:

```text
성분별 판매수량 = 해당 성분 태그가 붙은 SKU 판매수량 합계
성분별 판매금액 = 해당 성분 태그가 붙은 SKU 판매금액 합계
성분별 SKU수 = 해당 성분이 매칭된 SKU distinct count

성분 월별 추이 = 성분 × 월 기준 판매수량/판매금액 합계
```

커버리지:

```text
성분 매칭률 = 성분 키워드가 매칭된 SKU 수 / 전체 SKU 수 × 100
미매칭 SKU 수 = 전체 SKU 수 - 성분 매칭 SKU 수
```

## 17. 시즌 캘린더 화면 역할과 산식

화면명: 시즌 캘린더  
초기 화면 ID: `season`

목적:

- 기능구분/카테고리별 월별 수요 패턴과 피크월을 확인한다.
- 시즌성 강도가 높은 카테고리를 파악한다.

주요 산식:

```text
카테고리 월별 수요 = 카테고리 × 월 기준 판매수량 또는 판매금액 합계
피크월 = 12개월 중 수요가 가장 큰 월
활성월 평균 = 판매값이 0보다 큰 월들의 평균
피크 강도 = 피크월 수요 / 활성월 평균
```

히트맵 값:

```text
월별 히트맵 강도 = round((해당 월 수요 / 피크월 수요) × 10) + 1
최소값 2, 최대값 11로 보정
```

## 18. 교차분석 화면 역할과 산식

화면명: 교차분석

- 국가 × 카테고리
- 성분 × 브랜드

같은 조합을 비교해 특정 시장에서 강한 브랜드/SKU/성분을 찾는다.

기본 산식:

```text
교차 조합 판매수량 = 선택한 차원 조합별 판매수량 합계
교차 조합 판매금액 = 선택한 차원 조합별 판매금액 합계
조합 비중 = 조합 판매값 / 선택 범위 전체 판매값 × 100
```

활용:

- 특정 국가에서 강한 브랜드 찾기
- 브랜드별 핵심 국가 찾기
- 성분 트렌드와 국가/브랜드 연결
- 리포트 블록 후보 선정

## 20. SKU 집중도 화면 역할과 산식

라우트: `/order-analysis/sku-concentration`

목적:

- SKU별 판매금액 비중과 재고금액 비중을 비교해 재고 부족/과잉 가능성을 판단한다.

핵심 파일:

- `frontend/lib/sku-concentration.ts`
- `frontend/components/sku-concentration/SkuConcentrationClient.tsx`

주요 산식:

```text
판매 비중(%) = SKU 판매금액 / 선택 범위 전체 판매금액 × 100
재고 비중(%) = SKU 재고금액 / 선택 범위 전체 재고금액 × 100
비중 차이 = 재고 비중 - 판매 비중
```

판단:

```text
비중 차이 <= -부족 임계값이면 재고 부족 위험
비중 차이 >= 과잉 임계값이면 과잉 재고
그 외 적정
```

기본 임계값:

- 부족 임계값: 2.5%p
- 과잉 임계값: 3.0%p

등급:

```text
글로벌 판매비중 >= 8% 이면 A
글로벌 판매비중 >= 3% 이면 B
그 외 C
```

브랜드 의존도:

```text
Top1 SKU 비중 = 브랜드 내 1위 SKU 판매금액 / 브랜드 전체 판매금액 × 100
Top3 SKU 비중 = 브랜드 내 상위 3개 SKU 판매금액 합계 / 브랜드 전체 판매금액 × 100

Top3 >= 80% 이면 high
Top3 >= 50% 이면 medium
그 외 low
```

## 21. 최종 발주 화면 역할과 산식

라우트: `/integrated-order-review`

목적:

- 발주 분석 결과와 시즌 수요 큐를 통합해서 최종 발주 후보를 확인/수정/확정/제외한다.

구성:

- 발주분석에서 발주 필요로 판단된 SKU
- 시즌 분석에서 추가된 SKU 큐
- 최종 수량 수정
- 상태: 검토 중, 확정됨, 제외됨
- 확정 목록 CSV 내보내기

피크월 계산:

```text
SKU별 월별 판매수량 합계 중 가장 큰 월 = 피크월
```

권장 발주일 계산:

```text
다음 피크월 1일 = nextPeakDate(피크월)
권장 발주일 = 다음 피크월 1일 - 선택 운송수단 리드타임
```

운송수단 선택:

```text
해운, 철송, 트럭, 항공 후보를 리드타임 긴 순으로 정렬
피크까지 남은 일수 >= 리드타임인 후보 중 가장 긴 운송수단 선택
불가능하면 가장 짧은 운송수단 선택
```

긴급 여부:

```text
권장 발주일 <= 오늘이면 긴급
```

최종 수량:

```text
기본 최종 수량 = 발주분석 발주필요수량
사용자가 화면에서 수동 수정 가능
```

## 24. 코드 평가 시 중요한 관찰 포인트

### 1. 통합 워크스페이스가 매우 크다

`SiliconAnalyticsWorkspace.tsx`가 다수 화면, 데이터 로딩, 정렬, 리포트, 검색, UI 상태를 한 파일에 많이 포함하고 있다.

평가 포인트:

- 화면별 컴포넌트 분리 필요성
- 데이터 계산 로직과 UI 로직 분리 필요성
- 테스트 작성 난이도
- 유지보수성

### 2. 일부 화면 메트릭은 정적/샘플 값으로 보인다

`metrics` 객체에 화면별 상단 메트릭이 하드코딩되어 있다.

평가 포인트:

- 실제 API 결과와 연결된 값인지 확인
- 사용자에게 정적 값이 실데이터처럼 보이지 않는지 확인
- 하드코딩 메트릭 제거 또는 명확한 fallback 처리 필요

### 3. 발주 핵심 산식은 백엔드에 있고 화면에서도 재계산이 있다

백엔드:

- 발주필요수량
- 발주금액
- ETA 위험
- 운송 추천

프론트:

- MOI
- 미입고 반영 시나리오
- 재고 공백
- 상태 표시

평가 포인트:

- 동일 개념을 백엔드와 프론트에서 다르게 계산할 위험
- 산식 단일화 또는 API 응답에 계산 근거 포함 필요
- 숫자 불일치 발생 가능성

### 4. 본사 이동 수량이 현재 0으로 고정된다

`order_review.py`에서 `본사 이동 수량 = 0`으로 설정되어 있고, 추가 발주 필요 수량은 1차 부족수량과 같다.

평가 포인트:

- 본사 EU창고 재고 이동을 실제 발주 차감에 반영해야 하는지 정책 확인 필요
- 화면에서는 본사 이동/재고 보완을 언급하지만 산식에는 제한적으로 반영될 수 있음

### 5. 단가와 통화 처리 검증이 중요하다

EU 입고단가가 KRW/EUR인지에 따라 환율 적용 방향이 달라진다.

평가 포인트:

- 원천 파일 단가 통화 추론 정확도
- EUR/KRW fallback 사용 시 표시
- 0단가 제외 정책의 업무 적합성

### 6. 인사이트 화면은 API 결과, 로컬 저장, 프론트 재가공이 섞인다

국가/브랜드/SKU/시즌/성분 분석은 백엔드 집계 결과를 프론트가 다시 필터링/비중/피크월 계산에 활용한다.

평가 포인트:

- 백엔드와 프론트 집계 기준 일관성
- 기간 필터, 미분류 처리, 국가/권역 매핑 정확성
- 24개월 제한이 실제 업무 분석에 충분한지

### 7. 최종 발주 화면과 통합 워크스페이스의 `final` 정의가 다르다

`Screen` 타입과 title에는 `final`이 있으나, 실제 최종 발주 화면은 `/integrated-order-review` 별도 구현이다.

평가 포인트:

- 화면 구조 통일 필요
- 사용자가 어디에서 최종 발주를 해야 하는지 UX 명확성
- 중복된 최종 발주 개념 정리

## 25. 다른 AI에게 요청하면 좋은 평가 질문

다른 AI에게 코드를 평가받을 때 아래 질문을 그대로 전달하면 좋다.

1. 현재 발주필요수량 산식이 SCM 업무 관점에서 타당한가?
2. `안전재고 목표수량 - (EU 현지 가용수량 + 운송중 수량)` 방식이 미입고/본사재고/ETA를 충분히 반영하는가?
3. ETA 전 결품 위험 산식이 실제 재고 흐름을 과소/과대평가하지 않는가?
4. 프론트와 백엔드에서 중복 계산되는 MOI, 재고 공백, 상태 판단을 어디로 일원화하는 것이 좋은가?
5. `SiliconAnalyticsWorkspace.tsx`를 유지보수 가능한 구조로 나누려면 어떤 컴포넌트/훅/서비스로 분리해야 하는가?
6. 화면별 하드코딩 메트릭과 실데이터 메트릭을 어떻게 구분/정리해야 하는가?
7. 본사 EU창고 재고 이동 수량이 0으로 고정된 현재 로직이 업무 요구사항과 맞는가?
8. SKU 집중도에서 판매금액 비중과 재고금액 비중 차이로 부족/과잉을 판단하는 방식이 적절한가?
9. 시즌 피크월 기준 추천 발주월 계산이 운송 리드타임과 함께 충분히 현실적인가?
10. 국가/브랜드/SKU/성분 분석에서 미분류, 국가명 정규화, 카테고리 보정 로직의 리스크는 무엇인가?

## 26. 결론

이 웹사이트는 단순 대시보드가 아니라, 발주 의사결정과 수요 인사이트를 함께 다루는 SCM 분석 워크스페이스다.

핵심 가치는 다음 세 가지다.

1. SKU별 발주 필요 여부를 정량화한다.
2. ETA와 재고 소진일을 비교해 품절 공백을 선제적으로 찾는다.
3. 국가/브랜드/SKU/성분/시즌 데이터를 통해 발주 외의 수요 인사이트와 보고서까지 연결한다.

다만 코드 평가 관점에서는 `SiliconAnalyticsWorkspace`의 비대화, 하드코딩 메트릭, 프론트/백엔드 중복 산식, 본사 이동 수량 미반영, 최종 발주 화면 구조 불일치가 중요한 개선 후보로 보인다.
